# 开源项目洞察

## 核心理念

解读一个开源项目，产出的应是**技术解构与提炼**，不是文档翻译或使用教程。每篇解读回答的根本问题：这个项目解决了什么、架构怎么组织、核心实现怎么落地、有哪些值得借鉴的模式、与同类相比的优劣势。

**一个关键前提：** 本 skill 的解读产物默认是**要落进一个持续维护的 Markdown 知识库仓库**的。因此约定目录结构、索引同步与写作风格，是为了让这批解读在该仓库中可长期检索、可随上游演进——不是文档管理喧宾夺主，而是为"解读入库"这一具体场景服务的必要支撑。产出目录树、编号章节、索引三连、图表与写作规范，均以此为前提。

同时，解读文档最大的敌人是**幻觉**——模型编造不存在的文件、行号、接口。因此必须坚守一条铁律：

> **让程序验证，不让模型自证。**

模型只负责产出**内容**；凡是「这份论断是否真的对得上源码」的判断，一律交给程序用确定性的手段（子串匹配、路径校验、真实文件读取）去证实或纠正。解读文档里每一个 `文件:行号` 引用，都必须能经程序重定位回真实源码，可点开验证。

先判断模式，再动作。**先读现状，后动笔。**

## 何时使用 / 何时不用

### 何时使用
- 介绍一个全新的开源项目，知识库仓库里还没有它的解读文档 → **全新分析模式**
- 已解读的项目上游发新版 / 有重大变更，要更新或新增解读文档 → **增量模式**
- 对已有解读觉得深度不足，重新深入代码补充章节 → **增量模式**
- 要求解读输出必须**带真实源码引用**（文件路径 + 行号），可点击可验证、避免幻觉

### 何时不用
- 翻译官方文档 / 写使用教程（本 skill 不做这个）
- 项目专属约定（放项目的 instructions 文件，不进 skill）
- 纯静态需求可枚举、无代码解读深挖的场景，直接写死即可

**临时分析判别：** 本 skill 默认按"入库"规范执行（完整目录树 + 索引同步）。若用户只是要一段临场解读、明确不打算落进知识库仓库，产出主体解读即可，并主动告知"本次未做索引同步、未做落地目录判定"；若未声明，默认走完整入库流程（含下方的 `kb_repo` 判定）。

## 输入

### 源码：本地绝对路径

默认输入是**本地源码仓库的绝对路径**，例如 `/Users/me/src/wukong`。执行时：

1. 把该路径解析为统一的 `source_repo`，用 `os.path.realpath` 规范化并确认存在，作为后续所有真源引用验证的根。
2. 若用户只给远端地址（如 `github.com/xx/foo`）而非本地路径，先将其 `git clone`（`--depth=1` 浅克隆，避免大仓库拉取过慢/占用过大；若网络不可用，明确告知用户并请求本地路径）到本地再解读——真源验证必须读本地的真实文件，不能对着远端记忆写。
3. 所有 `文件:行号` 引用均以 `source_repo` 为根校验，防路径穿越（见"真源引用验证"一节）。

### 落地目标：知识库仓库判定（自动 + 确认兜底）

产出目录**不默认等同于**"执行 skill 时的当前工作目录"，而是先做一次判定，确认后记为 `kb_repo`。

**目标结构模式：** `{分类}/{项目名}/README.md`（+ 可选的 `01-xxx.md` 等分层文档），
例如 `IM/wukong/README.md`、`IM/wukong/01-arch.md`。顶层 `README.md`（总索引）是加分项，不是判定的必要条件——知识库仓库可能刚起步，还没来得及建总索引。

**判定信号（满足任一即视为"当前目录 = 目标知识库仓库"）：**
1. **结构扫描命中**：对当前目录做深度为 2 的扫描，存在至少一组 `{任意目录}/{任意目录}/README.md`（即"二级目录 + README.md"的组合），且该二级目录不是常见的源码工程目录名（如 `src`、`node_modules`、`cmd`、`internal`、`.git` 等需排除，避免把源码仓库本身的 `pkg/utils/README.md` 之类误判为知识库结构）；
2. **显式索引命中**：当前目录存在顶层 `README.md`，且其内容包含形如 `[分类](分类/README.md)` 或表格形式的模块索引链接——即已具备本 skill 规范里"顶层总索引"的雏形。

**排除信号（命中即视为不匹配，禁止直接落地）：**
- 当前目录就是本次要解读的 `source_repo` 本身，或是 `source_repo` 的子目录；
- 当前目录能识别出是某个具体编程项目的源码根（如存在 `package.json`/`go.mod`/`Cargo.toml` 等工程清单文件且无 md 知识库特征）——防止把"源码仓库"误判为"知识库仓库"；
- 当前目录是空目录且无任何 git/README 线索（无法判断意图，不能臆造）。

**执行逻辑：**
```
判定当前目录
├─ 命中判定信号 且 未命中排除信号 → 直接以当前目录为 kb_repo，落地
│
├─ 命中排除信号 → 停止，说明具体原因
│   （如"当前目录检测到 go.mod，疑似是源码目录而非知识库仓库"）
│   → 走下方"用户选择"分支
│
└─ 两类信号都未命中（拿不准）→ 展示扫描到的目录树摘要
   → 走下方"用户选择"分支
```

**用户选择分支（结构化二选一，不做开放式提问）：**

向用户说明判定结果后，给出两个选项：

1. **指定其他目录** —— 用户提供一个已存在的知识库仓库绝对路径，作为 `kb_repo`；若该路径不存在于本地（远端地址）先 clone 到本地；若该路径本身也不符合 `{分类}/{项目}/README.md` 结构，视为**全新知识库仓库**，按规范初始化。
2. **就在当前目录下新建** —— 以当前目录为 `kb_repo`，视为一个**全新的知识库仓库起点**，直接按输出规范创建 `{分类}/{项目}/README.md`，并新建顶层 `README.md` 索引雏形。

示例确认话术：
> "当前目录 {cwd} 未检测到 `分类/项目/README.md` 这类知识库结构（原因：{具体原因}）。
> 是否：
> ① 指定一个已有的知识库仓库路径
> ② 就在当前目录 {cwd} 下新建这套知识库结构
> 请选择，或直接给出目标路径。"

> **特别提示：** 若"用户选择分支"是由**排除信号**触发（如当前目录被识别为某源码工程根），选项②不作为默认推荐项，需在确认话术中额外提示：
> "注意：当前目录检测到 {go.mod/package.json 等}，看起来是一个代码仓库而非知识库仓库，在这里新建解读结构可能不是你想要的，请确认。"

用户选定后，记为 `kb_repo`，本次会话内后续的模式判定、落地、索引同步均以此为根，不再重复询问。

## 模式判定

前提：`kb_repo` 已经确认。

判断依据是 **`kb_repo/{分类}/{项目}/README.md` 是否已存在**：

- 存在 → **增量模式**（必须先读现有文档再动笔）。
- 不存在 → 在 `kb_repo` 下按 `*/*/README.md` 的 glob 模式全局扫描 + grep 项目名/仓库地址/常见别名，排除"已用别的分类名或项目别名建过索引"的情况（比如 wukong 之前被归类到 `chat/` 而不是 `IM/`）；
  - grep 命中 → 视为分类归属不一致导致的漏判，走增量模式，按命中位置定位真实文档，并向用户确认是否需要顺带纠正分类归属；
  - grep 未命中 → 确认是全新项目，走全新分析模式。

# 全新分析模式

新项目的冷启动解读。

1. **确立根因先行**。读项目自述/README，一句写出"解决什么根本问题"。这是全篇的锚，防止写成功能罗列。
2. **探索数据源（按序）**。README → 架构/设计文档 → 目录树（推模块划分）→ 核心模块代码 → 关键链路（启动流程 / 主请求链路）。
3. **定维度，非全覆盖**。从维度（概览/架构/认证/核心实现/存储/设计模式/部署/测试/社区/同类对比）里，选项目特点最突出的 2-4 个深入，不要每个都写一段。
4. **写字**，遵循下方"文档结构""真源引用验证""写作规范"。深度不足标 `[WIP]`/`TODO`，不要硬凑或只翻译。
5. **真源校验（不可跳过）**：提取本文档中所有 `[path:start-end]()` 引用 → 逐条跑 `ground_citations` 重定位 → 定位成功则用真实行号覆盖；定位失败则**保留原样并追加 `[UNVERIFIED]` 标记**，不静默通过，并在文末列出所有 `[UNVERIFIED]` 项提示人工复核。
6. **维护索引（收尾三步）**：在 `kb_repo` 下创建 `{分类}/{项目}/README.md` → 更新 `{分类}/README.md` 索引表 → 若分类尚不存在，在 `kb_repo` 顶层 README 添加新分类。
7. **提交边界**：本 skill 只负责落盘（写文件、更新索引），**不自动执行 `git add/commit/push`**。若 `kb_repo` 是 git 仓库，落地后应列出本次变更的文件清单，提示用户自行决定是否提交，不代为决策。

## 文档结构

两段必选 + 第三段起按项目特点自由选：

| 章节 | 内容 | 必选 |
|------|------|------|
| 第一部分：快速概览 | 是什么 / 痛点 / 适用场景 / 核心能力清单表 / 技术栈一览表 | ✅ |
| 第二部分：架构深读 | 架构总览图(Mermaid)/ 启动流程 或 请求链路 / 模块职责映射(目录树) | ✅ |
| 第三部分起 | 按项目特点深入:核心实现 / 设计模式 / 部署 / 同类对比 | 可选 |

输出可为单文件多部分，或主 README + 分层 md（如 `01-xxx.md`）。

## 输出规范（入库约定）

产出以 **Markdown 为主**，落在已确认的 `kb_repo` 下，按下述目录形态组织（参考成熟的解读目录实践）：

```
{kb_repo}/
├── README.md                # 顶层总索引（各技术分类 + 每个项目一行）
├── {分类}/                  # 按技术领域分类，如 IM/ auth/ rag/ devops/
│   ├── README.md            # 分类索引表：项目 | 语言 | 说明 | 协议 | 仓库
│   └── {项目}/
│       ├── README.md        # 项目解读主文档（`## 第X部分` 编号章节）
│       ├── 01-arch.md       # 可选：分层副文档（一个主题一篇）
│       └── arch.svg         # 可选：复杂架构图导出 SVG
```

- **主产出 = 项目解读页**（`{分类}/{项目}/README.md`），用 `## 第一部分` / `## 第二部分` 编号章节组织；内容过多时按主题拆成 `01-xxx.md` 副文档，README 内链接跳转。
- **分类归属**：按技术领域归类到对应 `{分类}/` 目录；不确定归入哪类、或需要新建分类时，向用户确认。
- **索引同步（收尾三步）**：建 `{分类}/{项目}/README.md` → 更新 `{分类}/README.md` 索引表 → 若分类尚不存在则新建分类并加入 `kb_repo` 顶层 `README.md`。
- **Markdown 内部可渲染格式**（无需额外工具，GitHub / VS Code 即原生支持）：
  - 图表：` ```mermaid ` 代码块。
  - 对照 / 数据 / 清单：Markdown 表格。
  - 线性流程：ASCII 列表图（≤15 行）。
- **可选 SVG**：仅当遇到**大型或需定制视觉的复杂架构图**（节点多、需配色/标注/缩放）时，额外导出独立 `.svg` 文件，用 `![架构](arch.svg)` 嵌入同名目录的 md 中。**本 skill 不绑定任何特定的 SVG 生成 skill**——实现方式按效果自选，只保证产出是自包含、可离线打开、视觉清晰的 `.svg`。mermaid 代码块与 SVG **二选一**，不要为同一张图重复产出。
- **命名**：分层副文档 `01-xxx.md`、`02-xxx.md`；图文件与引用它的 md 同目录。

# 增量分析模式

对**已有解读文档**做更新或补充。**变更的唯一依据 = 上游 git diff / release notes**，禁止凭空重写或凭个人偏好重排。若拿不到 git diff / release notes（本地仓库无 `.git` 历史、上游未写 changelog），退化为**代码快照比对**：对比当前代码与既有文档描述的差异点，并在文中显式声明"本次依据代码快照比对，非官方 changelog"。

## 铁律（违反即重来）

1. **先读现有文档，再动笔。** 不先读就改 = 失败。
2. **差异驱动。** 每处变更必须能追溯到上游 diff / release notes（或声明过的代码快照比对）。找不到依据的改动不要做。
3. **确认覆盖范围。** 先定位现有文档已覆盖的内容，避免重复。先在仓库或上游核对**真实地址与版本**，拿到实际 release 变更或 git diff 作依据，而不是只信口头描述。
4. **最小破坏结构。** 已有编号章节（`## 第X部分`）原样保留，不移动、不删除、不重排标题。

## 变更粒度（从轻到重，够用就好）

1. **改段落** —— 更新"现状描述"里过时的数字/表述。
2. **加独立 md** —— 新增一个主题就新建 `xx.md`，别把 README 主体越堆越长。
3. **重排主体结构** —— 仅在确有必要时调整，几乎不该发生。

> 同一项目的版本演进优先**就地编辑 + 演进说明**，不要为它新建文件、破坏单文档强编号结构。

## 范围界定（什么值得写）

**值得写：** 影响"现状描述一致性"的数字（引擎数、默认库、接口数量）；新增的独立能力点；用户可感知的接入/用例变化。
**不值得写：** 为每个历史版本加脚注造成噪音；拆分新文件只为了不破坏结构；修改**竞品**行的描述（它不是本项目的组件）。

## 结构保护与演进标注

- 新增小节用 `###` 三级标题，与同部分兄弟小节平级，不进编号章节。
- 删掉的现状数字不直接抹掉，用 `> **演进说明(版本号)**` 引用块保留历史轨迹，再写新现状。
- 文档头更新版本号，并加一段"本版增量更新说明"，列出相比上一版的主要变更。
- 能力清单、技术栈表、架构图、对比表里的数字要**同步更新**，只改正文会漏。全篇 grep 核对一致性。
- 同"全新分析模式"步骤 5，改完后重新跑一遍真源校验，新增/改动的引用同样要经程序重定位，失败标 `[UNVERIFIED]`。
- 落盘后同样只提示变更清单，不代为 `git commit`。

# 真源引用验证（Grounding）——防幻觉核心

解读文档里的引用要落地，核心是这一节。它保证阅读者点开的每一处论断都能对上真源码。

### 思想

模型给的行号是**猜的**，但模型从上下文**原样复制的 snippet 是可信指纹**。与其信行号，不如把 snippet 当线索去真实源码文件里搜索，算出真实行号。程序负责验证，不让模型自证。

### 关键约束（写进解读要求）

- 引用的 `snippet` 字段**必须从源码上下文逐字复制**，不得改写、不得凭记忆拼。
- 引用路径用**仓库相对路径 + 行号**，格式统一为 `模块/子目录/文件名.ext:行号`（示例以 Go 为例，实际按项目语言替换后缀，如 `.ts`/`.py`/`.rs`），禁止使用裸文件名（如 `utils.go` 必须写成 `pkg/utils/util.go:42`）。
- 引用链接留空括号 `[path:start-end]()`，由程序统一补成真实 URL + 行锚点；落库前须经程序重定位，用真实行号覆盖模型给的行号。
- **定位失败不允许静默放过**：找不到匹配的引用必须保留原样并追加 `[UNVERIFIED]` 标记，在文末汇总列出，交由人工复核，不能与已验证的引用长得一样。

### 核心实现（Python，可迁移，作为验证工具参考）

```python
# snippet 作为指纹，在真实源码里精确定位行号
def locate_snippet(text: str, snippet: str):
    snippet = snippet.strip("\n")
    if not snippet:
        return None
    pos = text.find(snippet)                       # ① 精确整段搜索
    if pos != -1:
        start = text.count("\n", 0, pos) + 1
        return start, start + snippet.count("\n")
    # ② 退化策略：以 snippet 首非空行为锚点
    first = next((ln.strip() for ln in snippet.splitlines() if ln.strip()), "")
    if first:
        idx = text.find(first)
        if idx != -1:
            start = text.count("\n", 0, idx) + 1
            return start, start + snippet.count("\n")
    return None

# 逐条重定位模型给出的引用
def ground_citations(citations, repo_dir):
    for cit in citations:
        if not cit.snippet or not cit.file_path:
            continue
        path = os.path.join(repo_dir, cit.file_path)
        try:
            with open(path, "r", encoding="utf-8") as f:
                text = f.read()
        except OSError:
            cit.verified = False
            continue
        loc = locate_snippet(text, cit.snippet)
        if loc:
            cit.start_line, cit.end_line = loc       # 真实行号覆盖模型行号
            cit.verified = True
        else:
            cit.verified = False                     # 定位失败：显式标记，不静默放过
```

### 配套安全：读文件必须防路径穿越

```python
repo_dir = os.path.realpath(repo_dir)
target = os.path.realpath(os.path.join(repo_dir, file_path))
if os.path.commonpath([repo_dir, target]) != repo_dir:
    raise ValueError("Resolved path escapes the repository directory")
```

用 `realpath` 消除 `../` 与符号链接，再用 `commonpath` 确保目标仍在仓库根内——防止 `../../etc/passwd` 一类任意文件读取。此校验同样适用于对 `kb_repo` 的任何读写操作。

**教训**：若解读走 RAG（代码量大的仓库），切分时就要给每个 chunk 记录真实起始/结束行号（切分器对每个 chunk 独立复制 `meta_data`），否则后续落点无据可依。

# 写作规范（入库约定）

- 中文为主，技术术语保留英文（ForwardAuth、JWT、sqlc）。
- 代码块标注语言：`go`/`ts`/`yaml`/`sql`。
- 未完成章节用 `[WIP]`，待补充用 `TODO`；列表统一用 `-`。
- **代码引用统一为 `文件:行号` 且需经真源重定位验证**，禁止写记忆中的行号与路径；定位失败一律标 `[UNVERIFIED]`。

# Mermaid 与图表约束（入库约定）

图表是解读的可视化支撑，但必须是"可渲染、可核对"的，不允许留下渲染报错的图。

**类型映射：**

| 图表用途 | Mermaid 类型 | 说明 |
|---------|-------------|------|
| 架构总览 | `graph TB` / `graph LR` | 模块层次、整体架构 |
| 流程图 / 启动流程 | `graph TB` | 步骤、请求链路、程序流程 |
| 时序图 | `sequenceDiagram` | 模块间交互、请求时序 |
| 状态图 | `stateDiagram-v2` | 状态流转、生命周期 |

**规模与原则：**

- 图谱控制在 **15 节点以内**，太复杂就拆成多个图，分别标注主题。
- 不追求面面俱到——抓关键链路，标注核心数据流方向。
- 线性流程（如启动流程）直接用 ≤15 行的列表式 ASCII 图，可读性更好。
- 落盘前**确认 Mermaid 语法可渲染**，不保留报错的图。

**与 SVG 的分工：**

- 默认用 md 内嵌的 ` ```mermaid ` 代码块（零成本，平台原生渲染）。
- 仅当需定制视觉 / 架构过大时，才导出独立 `.svg` 嵌入；同一张图不做 mermaid + svg 双份。

# 常见错误与对策

| 错误 | 修正 |
|------|------|
| 信任模型/记忆的行号 | 只信 verbatim snippet，程序在真实文件重定位真行号。 |
| 定位失败当作定位成功一样处理 | 失败必须标 `[UNVERIFIED]`，不能和已验证引用长得一样。 |
| 没先读现有文档就重写 | 增量铁律 1：先读。 |
| 凭感受大改结构 | 结构是资产，编号章节原样保留。 |
| 只改正文、漏掉能力清单/技术栈/图表里的数字 | 全篇 grep 核对所有出现处。 |
| 文档自称 v0.8 却没核对真实上游版本/diff | 增量铁律 3：先取真实依据；拿不到就声明代码快照比对。 |
| 新建文档后忘了更新分类索引 | 收尾三步不能跳。 |
| 把 README 翻译一遍充深度 | 这是提炼，不是翻译；深度不足标 [WIP]。 |
| 单文件暴力拼全部源码进提示词 | 超 token 且污染上下文；中小库打包相关文件，大库走 RAG。 |
| 引用用裸文件名不对应真实路径 | 一律仓库相对路径 `模块/子目录/文件.ext:行号`，防穿越校验后落库。 |
| 引用无行号 | 引用须带真实行号，用 snippet 在真实文件重定位后补齐。 |
| 把 cwd 当成知识库仓库直接写入 | 先做 kb_repo 判定，命中排除信号或拿不准时必须走用户选择分支。 |
| 把源码仓库误判为知识库仓库 | 检查 go.mod/package.json 等工程清单文件，命中即视为排除信号。 |
| 图渲染报错或 mermaid+svg 重复 | 落盘前校验可渲染；同一张图只保留一种形式。 |
| 读源码文件无路径防护 | `realpath` + `commonpath` 白名单校验，防任意文件读取，对 kb_repo 同样适用。 |
| 落盘后擅自 git commit | 只列变更清单，是否提交交给用户决定。 |

# Quick Reference

- 判断落地目标：先扫描当前目录是否符合 `分类/项目/README.md` 结构 → 符合则直接用；命中排除信号或拿不准 → 结构化二选一（指定新目录 / 就在当前目录新建），确认后记为 `kb_repo`。
- 判断模式：`kb_repo/分类/项目/README.md` **存在** → 增量；不存在（且 grep 无别名命中）→ 全新。
- 输入：本地源码绝对路径 → `source_repo` 为验证根；远端先浅克隆；`kb_repo` 同理支持远端。
- 输出：`{kb_repo}/{分类}/{项目}/README.md` + `{分类}/README.md` 索引 + 顶层 `README.md`；主 md，可选 `01-*.md` 分层与 `.svg` 复杂图。
- 增量铁律：先读 → 差异驱动（git diff / release notes 为唯一依据，拿不到则声明代码快照比对）→ 最小破坏 → 同步数字与索引。
- 变更粒度：改段落 → 加独立 md → 重排主体（几乎不用）。
- 真源验证：snippet 是可信指纹，模型行号是猜的 → 在真实文件重定位覆盖；定位失败标 `[UNVERIFIED]`；引用用仓库相对路径 `文件.ext:行号` + 防穿越校验。
- 图表：Mermaid ` ```mermaid ` 为主（≤15 节点、落盘前校渲染），超大/定制视觉才导 `.svg`，不重复。
- 收尾（全新）：建项目 README → 更新分类索引 → 必要时顶层 README → 列变更清单，不代为 commit。
- 质量红线：kb_repo 判定 / 能力表 / 技术栈表 / Mermaid 图 / 链路 / ≥2 处真源引用 / 根因 / 索引同步 / 引用程序验证（含 UNVERIFIED 标记）/ 图表可渲染。
