# 量化与量级估算（quantification）

方案里「高并发」「存储量很大」「可用性 99.99%」这类话无法被评审，也无法被验证。本文回答三件事：**什么时候必须给数字、数字怎么推、常见量级是多少**。

## 一、触发条件：出现这些论断就必须量化

| 论断类型 | 必须给出 |
|----------|----------|
| 性能（RT / 吞吐） | 目标值 + 分位口径（P50/P99）+ 测量点（服务端/端到端）+ 现状基线 |
| 容量（存储/带宽/连接数） | 单条大小 → 增量速率 → 规划期总量（含副本与索引膨胀系数） |
| 规模（QPS/TPS/并发） | 平均值 + 峰值系数 + 推导过程（谁乘谁） |
| 可用性 | 目标几个 9 + 端到端还是单组件 + 串并联预算 |
| 成本 | 单价 × 用量 + 计费口径；给区间而非单点 |

给不出数字时，正确写法是显式假设，而不是省略：

> **待验证假设**：假设日均活跃 5 万、人均 20 次请求 → 峰值 QPS ≈ 120（峰值系数 5）。若实际峰值系数大于 10，缓存层需从单实例改为集群（见「扩容触发阈值」）。

## 二、估算链条（五步，按序推）

1. **规模输入**：用户量 → 活跃比例 → 日请求数 → 读写比 → **峰值系数**（通常 2–10：To C 白天高峰取 5 左右，定时任务型取 1–2，秒杀类取 10+）。
2. **单条数据**：字段级拆解求和（业务字段 + 主键外键 + 时间戳 + 索引开销），不要凭感觉给一个整数。
3. **存储量**：单条 × 条数 × **膨胀系数**（索引 + 副本 + 预留，经验上 ×2–3）→ 日/月/年增量 → 规划期总量（一般按 3 年）。
4. **吞吐**：平均 QPS = 日请求数 ÷ 86400（≈10⁵ 秒）；峰值 QPS = 平均 × 峰值系数。单机承载能力按**最慢环节**（DB 写、外部调用）估，而不是按 CPU。
5. **资源**：带宽 = 峰值 QPS × 单次传输字节；内存 = 热点条目数 × 单条内存占用 × 冗余系数；连接数 ≈ 峰值 QPS × 平均处理耗时（Little's Law）。

**完整示例（短链服务）**：1000 万用户、月写入 1000 万次、月读取 1 亿次 → 读写比 10:1；单条 ≈ 1KB 正文 + 7B 短码 + 4B 过期时间 + 5B 创建时间 + 255B 路径 ≈ 1.27KB；月增 ≈ 12.7GB，3 年 ≈ 450GB（未计副本，计副本 ≈ 1TB+）；平均写 4/s、读 40/s。

## 三、常用换算

- 时间：1 天 ≈ 86,400s ≈ 10⁵s；1 月 ≈ 2.6×10⁶s；1 年 ≈ 3.15×10⁷s
- 请求：1 亿 req/天 ≈ 1,160 req/s（平均）；250 万 req/s ≈ 1.5 亿 req/min；1 亿 req/min ≈ 1.7 万 req/s
- 带宽：1 Gbps ≈ 125 MB/s（理想值）；1 万 QPS × 单次响应 10KB = 100 MB/s ≈ 0.8 Gbps（已接近单口上限）
- 容量近似：2¹⁰≈10³、2²⁰≈10⁶、2³⁰≈10⁹、2⁴⁰≈10¹²（分别约 1KB/1MB/1GB/1TB 量级）

## 四、延迟与带宽量级参考

用途是判断「是否必须加缓存 / 换介质 / 减少跨机房调用」。这些是**数量级参考，不是硬指标**（公开口径，SSD 与网络数字偏保守，随硬件演进）。

| 操作 | 量级 |
|------|------|
| L1 缓存访问 | 0.5 ns |
| 分支预测失败 | 5 ns |
| L2 缓存访问 | 7 ns |
| 互斥锁加解锁 | 25 ns |
| 内存访问 | 100 ns |
| 压缩 1KB | 10 μs |
| 1Gbps 网络发送 1KB | 10 μs |
| SSD 随机读 4KB | 150 μs |
| 内存顺序读 1MB | 250 μs |
| **同机房一次往返（RTT）** | **500 μs** |
| SSD 顺序读 1MB | 1 ms |
| HDD 寻道 | 10 ms |
| 跨洲一次往返 | 150 ms |

派生吞吐：内存顺序 ≈ 4 GB/s、SSD 顺序 ≈ 1 GB/s、1Gbps 网 ≈ 100 MB/s、HDD 顺序 ≈ 30 MB/s。

**用法**：写「这里必须加缓存」时，理由应是「内存 100ns vs SSD 随机读 150μs vs 同机房往返 500μs，差 3–4 个数量级」；写「跨机房调用要合并或改异步」时，理由应是「一次跨洲往返 150ms，几次串行即突破 RT 目标」。

## 五、可用性算术

### 几个 9 意味着多少停机

| 可用性 | 年停机 | 月停机 | 日停机 |
|--------|--------|--------|--------|
| 99% | 3.65 天 | 7.2 小时 | 14.4 分钟 |
| 99.9%（3 个 9） | 8 小时 46 分 | 43 分 50 秒 | 1 分 26 秒 |
| 99.95% | 4 小时 23 分 | 21 分 55 秒 | 43 秒 |
| 99.99%（4 个 9） | 52 分 36 秒 | 4 分 23 秒 | 8.6 秒 |
| 99.999%（5 个 9） | 5 分 15 秒 | 26 秒 | 0.86 秒 |

### 串联与并联

- **串联**（链路必须全通）：`A = Π Aᵢ` —— 3 个 99.9% 串起来只有 **99.7%**（年停机约 26 小时）。
- **并联**（冗余，任一可用即可）：`A = 1 − Π(1 − Aᵢ)` —— 2 个 99.9% 并联 ≈ **99.9999%**。

**预算规则**：先写下端到端目标，再按串联段数分摊，不要给每个组件都写 99.99%。例：端到端目标 99.99%（年 52 分钟），链路 4 段串联 → 每段至少 ~99.9975%，或对关键段做并联冗余。成稿时把这张「可用性预算表」放进「约束与非功能需求」或「验收标准」。

## 六、反模式（出现即返工）

- 「高并发场景」而不给 QPS 与峰值系数。
- 「存储量很大」「成本可控」而不给单条大小 / 单价与用量口径。
- 「可用性 99.99%」而不说是端到端还是单组件、不做串联预算。
- 把峰值当平均，或直接抛出「预计 10 万 QPS」而无推导。
- 只给单点值不给区间；有不确定性的量不做敏感度说明（「若 DAU 翻倍，3 年存储从 450GB 到 900GB」）。
