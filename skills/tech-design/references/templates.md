# 模板档位（templates）

三档骨架决定**篇幅与评审范围**；档位由 SKILL.md 的定档表选择，专题加固见 `focus-areas.md`。

骨架综合了主流方案/设计文档实践：Google Design Doc 的「目标/非目标 + 备选方案」、Rust RFC 的「开放问题分类收口」、ADR 决策记录，以及国内评审的「验收标准 / 发布回滚」惯例（对照见文末）。

## 通用约定（读骨架前先读这段）

1. **骨架是覆盖清单，不是填空卷**。不适用的章节**删掉**，不要留 "N/A" 或一句话占位——占位章节比缺章节更伤可信度。
2. **章节名是语义示例**，随主题替换；不加「1. 2.」数字前缀（用户明确要求编号时，可在成稿时补，但不写进模板）。
3. **非目标用「超出范畴的用例」表述**，比否定句可评审：
   - 弱：「不做权限管理」。
   - 强：「超出范畴的用例：本期不覆盖跨租户数据共享、不提供字段级权限；原因是这两项需要独立的权限模型，计划在二期立项（见开放问题）」。
4. **验收标准必须可验证**：谁验、怎么验、阈值多少。凡涉及性能/容量/可用性的阈值，按 `quantification.md` 给推导与口径。
5. **不确定项集中收口**：评审需拍板的、实现中才能定的、范围外后续做的——分三类落在「开放问题」，不要散在正文里含糊。

## 档位速览

| 档位 | 目标篇幅 | 典型读者 | 定位 | 选错档的信号 |
|------|----------|----------|------|--------------|
| 轻量 | 1-2 屏 | 本模块开发者 / 一次评审 | 说清做什么、怎么实现、取舍与风险 | 出现跨团队依赖、存量数据迁移、SLA 承诺 → 上浮到标准档 |
| 标准 | 2-5 屏 | 团队评审 | 完整方案 + 详细设计 + 计划 + 验收 | 出现多系统联动、成本敏感、不可逆变更 → 上浮到完整档 |
| 完整 | 长文（分章节阅读） | 架构评审委员会 / 跨团队 | 全链路评估，含容量/安全/成本/回滚 | 只有单个模块改动、无跨系统影响 → 下沉，避免过度设计 |

## 轻量档

适用：单个功能模块、小型优化、简单集成。只回答「背景、思路、取舍、怎么落、有什么风险」，默认**不写**成本/容灾/压测/可观测等企业级章节。

```markdown
# [主题]技术方案

## 背景与目标
### 现状与问题
（当前怎么做的、痛点具体在哪，一句话能说清就够）
### 目标与非目标
（非目标 = 超出范畴的用例，至少 1 条，并给原因）
### 验收标准
（一句话：上线后如何衡量；或「一次评审通过即可」）

## 核心设计
### 设计思路
### 备选与取舍
（≥2 种做法，写清为何不选更重/更轻的那个）
### 技术选型
（1-2 句取舍理由即可，含代价）
### 实现要点
（核心步骤或最小示例片段；代码原则见 quality-bar.md）

## 实施计划
### 实施步骤
### 时间估算（给区间，注明假设）

## 风险与应对
### 主要风险
### 应对措施（含回滚/降级：触发条件 + 具体动作）

## 待确认问题（可选）
（评审前需要拍板的点，标注默认倾向，避免正文含糊）
```

## 标准档

适用：子系统、中型业务模块。在轻量档基础上补「现状痛点、约束与验收、总体方案、详细设计、里程碑、备选方案否决记录」。

```markdown
# [主题]技术方案

## 背景与目标
### 业务背景与现状
### 痛点分析
### 目标与非目标
（非目标写成「超出范畴的用例」并给原因）
### 约束与非功能需求
（性能/可用性/一致性/安全/合规约束的定位与量化目标，细节后置到对应章节；
 可用性目标需给端到端口径与串联预算，见 quantification.md）
### 验收标准
（量化指标 + 验证方式 + 责任方，作为评审通过基线）

## 方案设计
### 总体思路
### 总体架构（图用 Mermaid，规范见 quality-bar.md）
### 核心流程
### 备选方案与取舍
（整体层面：自研 vs 改造 vs 引入现成 vs 分阶段；每个方案写代价与否决理由）
### 技术选型与理由
（组件级 2-3 方案对比：适用场景、代价、什么情况下不该选）

## 详细设计
### 模块划分与职责
### 接口设计
### 数据模型
### 关键逻辑与算法（按需）

## 实施计划
### 阶段与里程碑（每阶段可独立上线）
### 资源需求
### 时间估算

## 风险评估与应对
### 技术风险
### 业务风险
### 应对措施（含降级/回滚：触发条件 + 动作 + 验证）

## 待确认与开放问题（可选）
（分三类收口：评审需拍板 / 实现中解决 / 范围外后续）

## 附录
### 参考资料
### 术语说明
```

## 完整档

适用：系统架构、跨系统集成、技术重构、大型平台。在标准档基础上展开摘要、系统上下文、上线与回滚、成本、开放问题、决策记录等企业级章节。

```markdown
# [主题]技术方案

## 摘要（TL;DR）
（评审先读的一页：结论、核心取舍、量化目标、主要风险、需要谁拍板）

## 背景与目标
### 业务背景与现状
### 痛点与动因
### 目标与非目标
（非目标即「超出范畴的用例」，逐条给原因，防止评审期范围反复）
### 约束与非功能需求
（性能/可用性/一致性/安全/合规/兼容约束；可用性给端到端口径 + 串联预算表）
### 验收标准
（量化指标 + 口径（平均/P99）+ 验证方式 + 责任方）

## 总体架构设计
### 架构设计原则
### 系统上下文与依赖
（外部系统/依赖方/数据来源与去向，可配 context 图）
### 总体架构（图用 Mermaid）
### 系统边界与职责
### 核心流程
### 数据流转

## 详细技术设计
### 模块划分与职责
### 接口设计
### 数据模型
### 存储设计
### 缓存设计（含失效策略与穿透/雪崩防护）
### 消息与异步（如适用）
### 关键算法与核心逻辑

## 方案与选型对比
### 备选方案
（整体层面：自研 vs 改造 vs 引入现成 vs 分阶段；各方案代价与否决理由）
### 技术选型对比
（组件级 ≥2-3 方案：适用场景、代价、不该选的场景）
### 选型风险与回退路径

## 性能与容量设计
### 性能目标与基线
### 容量规划（存储/带宽/连接的规划期总量 + 扩容触发阈值）
### 优化策略（每项：预期收益 + 代价 + 回退开关）
### 压测方案（场景、数据量、通过判据）

## 安全设计
### 认证与授权
### 数据安全
### 接口安全
### 容灾与备份

## 可观测性设计
### 监控告警（关键指标 + 阈值 + 告警触达）
### 日志（含脱敏要求）
### 链路追踪

## 上线与回滚方案
### 发布计划（灰度/分批/开关）
### 兼容性与数据迁移（协议/数据/存量兼容）
### 回滚方案（触发条件 + 步骤 + 回滚后验证 + 是否可逆）

## 实施计划
### 阶段与里程碑
### 资源需求
### 时间估算
### 依赖与前置条件

## 成本分析
### 开发成本
### 运维成本
### 硬件/云资源成本（单价 × 用量 + 计费口径）

## 风险评估与应对
### 技术风险
### 业务风险
### 进度风险
### 应对措施（降级/回滚/预案；详细回滚步骤见「上线与回滚方案」）

## 开放问题与后续工作
（分三类收口：评审需拍板 / 实现中解决 / 范围外后续独立做）

## 附录
### 参考资料
### 术语说明
### 决策记录（ADR：结论 + 备选 + 理由，便于日后回溯）
```

> 完整档不内嵌「评审检查清单」章节：清单为单一真源，统一在 `quality-bar.md`，收尾时按档位与专题生成。

## 对齐的主流模板（维护备注）

- **Google Design Doc**：Goals / Non-Goals（非目标 = 本可以做但明确不做）、备选方案、系统上下文。
- **Rust RFC 模板**：Motivation 先行、Unresolved questions 分类收口。
- **ADR（Architecture Decision Records）**：决策以「结论 + 备选 + 理由」沉淀，落在完整档附录。
- **国内方案评审惯例**：验收标准、发布/灰度/回滚、排期与资源显式化。
