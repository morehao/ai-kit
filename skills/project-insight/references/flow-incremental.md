# 增量分析模式

> 由 SKILL.md「执行流程主干」的 step 1 判定为**增量模式**（已有解读文档）时按需加载。对**已有解读文档**做更新或补充。**变更的唯一依据 = 上游 git diff / release notes**，禁止凭空重写或凭偏好重排。拿不到 git diff / release notes（本地仓库无 `.git` 历史、上游未写 changelog）时退化为**代码快照比对**：对比当前代码与既有文档描述差异，并在文中显式声明"本次依据代码快照比对，非官方 changelog"。

## 铁律（违反即重来）

1. **先读现有文档，再动笔。** 不先读就改 = 失败。
2. **差异驱动。** 每处变更必须能追溯到上游 diff / release notes（或声明的代码快照比对）。找不到依据的改动不做。
3. **确认覆盖范围。** 先定位现有文档已覆盖内容，避免重复；先在仓库或上游核对**真实地址与版本**，取实际 release 变更或 git diff 为依据，不只听口头描述。
4. **最小破坏结构。** 已有 `##` 章节标题原样保留，不移动、不删除、不重排标题。

## 变更粒度（从轻到重，够用就好）

1. **改段落** —— 更新"现状描述"里过时的数字/表述。
2. **加独立 md** —— 新增一个主题就新建 `xx.md`，别把 README 主体越堆越长。
3. **重排主体结构** —— 仅在确有必要时，几乎不该发生。

> 同一项目的版本演进优先**就地编辑 + 演进说明**，不为此新建文件、不破坏单文档强编号结构。

## 范围界定（什么值得写）

**值得写：** 影响"现状描述一致性"的数字（引擎数、默认库、接口数量）；新增的独立能力点；用户可感知的接入/用例变化。
**不值得写：** 为每个历史版本加脚注造成噪音；拆分新文件只为了不破坏结构；修改**竞品**行描述（它不是本项目组件）。

## 结构保护与演进标注

- 新增小节用 `###` 三级标题，与同部分兄弟小节平级，不挤进顶层 `##` 章节层级。
- 删掉的现状数字不直接抹掉，用 `> **演进说明(版本号)**` 引用块保留历史轨迹，再写新现状。
- 文档头更新版本号，加一段"本版增量更新说明"，列出相比上一版的主要变更。
- 能力清单、技术栈表、架构图、对比表里的数字要**同步更新**，只改正文会漏。全篇 grep 核对一致性。
- 真源校验与全新分析流程一致：改完后重跑一遍 `scripts/verify-references.mjs` 与 `scripts/check-mermaid.mjs`（用法见 [grounding-guide.md](grounding-guide.md)），新增/改动的引用同样经程序重定位，失败标 `[UNVERIFIED]`；`[MERMAID-ERROR]` 修复至全 `OK`。
- 落盘后同样只提示变更清单，不代为 `git commit`。
