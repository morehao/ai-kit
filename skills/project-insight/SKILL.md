# 开源项目洞察

## 核心理念

解读一个开源项目，产出的应是**技术解构与提炼**，不是文档翻译或使用教程。每篇解读回答的根本问题：这个项目解决了什么、架构怎么组织、核心实现怎么落地、有哪些值得借鉴的模式、与同类相比的优劣势。

**一个关键前提：** 本 skill 的解读产物默认是**要落进一个持续维护的 Markdown 知识库仓库**的。因此约定目录结构、索引同步与写作风格，是为了让这批解读在该仓库中可长期检索、可随上游演进——不是文档管理喧宾夺主，而是为"解读入库"这一具体场景服务的必要支撑。产出目录树、编号章节、索引三连、图表与写作规范，均以此为前提。

同时，解读文档最大的敌人是**幻觉**——模型编造不存在的文件、行号、接口。因此必须坚守一条铁律：

> **让程序验证，不让模型自证。**

模型只负责产出**内容**；凡是「这份论断是否真的对得上源码」的判断，一律交给程序用确定性的手段（子串匹配、路径校验、真实文件读取）去证实或纠正。解读文档里每一个 `文件:行号` 引用，都必须能经程序重定位回真实源码，可点开验证。

先判断模式，再动作。**先读现状，后动笔。**

## 何时使用 / 何时不用

### 何时使用
- 介绍一个全新的开源项目，仓库/分析目录里还没有它的解读文档 → **全新分析模式**
- 已解读的项目上游发新版 / 有重大变更，要更新或新增解读文档 → **增量模式**
- 对已有解读觉得深度不足，重新深入代码补充章节 → **增量模式**
- 要求解读输出必须**带真实源码引用**（文件路径 + 行号），可点击可验证、避免幻觉

### 何时不用
- 翻译官方文档 / 写使用教程（本 skill 不做这个）
- 项目专属约定（放项目的 instructions 文件，不进 skill）
- 纯静态需求可枚举、无代码解读深挖的场景，直接写死即可

**临时分析判别：** 本 skill 默认按"入库"规范执行（完整目录树 + 索引同步）。若用户只是要一段临场解读、明确不打算落进知识库仓库，产出主体解读即可，并主动告知"本次未做索引同步"；若未声明，默认走完整入库流程。

## 输入

### 源码：本地绝对路径

默认输入是**本地源码仓库的绝对路径**，例如 `/Users/me/src/tinyauth`。执行时：

1. 把该路径解析为统一的 `repo_dir`，用 `os.path.realpath` 规范化并确认存在，作为后续所有真源引用验证的根。
2. 若用户只给远端地址（如 `github.com/xx/foo`）而非本地路径，先将其 `git clone` 到本地再解读——真源验证必须读本地的真实文件，不能对着远端记忆写。
3. 所有 `文件:行号` 引用均以 `repo_dir` 为根校验，防路径穿越（见"真源引用验证"一节）。

### 产出目录：执行 skill 所在的工作目录

解读产物落在**执行 skill 时的当前工作目录**（例如 `/Users/me/Documents/study/doc-tools/oss-insights`），就地按"输出规范"组织，不做跨目录搬运。

## 模式判定

判断依据是**该项目的分析文档目录是否已存在**：

- 目录存在 → **增量模式**（必须先生读现有文档再动笔）。
- 目录不存在 / 拿不准是否符合既有目录 → 先查项目顶层 README 的分类索引与既有模块，可能是**漏建索引**而非全新项目。

# 全新分析模式

新项目的冷启动解读。

1. **确立根因先行**。读项目自述/README，一句写出"解决什么根本问题"。这是全篇的锚，防止写成功能罗列。
2. **探索数据源（按序）**。README → 架构/设计文档 → 目录树（推模块划分）→ 核心模块代码 → 关键链路（启动流程 / 主请求链路）。
3. **定维度，非全覆盖**。从维度（概览/架构/认证/核心实现/存储/设计模式/部署/测试/社区/同类对比）里，选项目特点最突出的 2-4 个深入，不要每个都写一段。
4. **写字**，遵循下方"文档结构""真源引用验证""写作规范"。深度不足标 `[WIP]`/`TODO`，不要硬凑或只翻译。
5. **维护索引（收尾三步）**：创建 `模块/项目/README.md` → 更新 `模块/README.md` 索引表 → 若模块尚不存在，在顶层 README 添加新分类。

## 文档结构

两段必选 + 第三段起按项目特点自由选：

| 章节 | 内容 | 必选 |
|------|------|------|
| 第一部分：快速概览 | 是什么 / 痛点 / 适用场景 / 核心能力清单表 / 技术栈一览表 | ✅ |
| 第二部分：架构深读 | 架构总览图(Mermaid)/ 启动流程 或 请求链路 / 模块职责映射(目录树) | ✅ |
| 第三部分起 | 按项目特点深入:核心实现 / 设计模式 / 部署 / 同类对比 | 可选 |

输出可为单文件多部分，或主 README + 分层 md（如 `01-xxx.md`）。

## 输出规范（入库约定）

产出以 **Markdown 为主**，落在执行 skill 的工作目录下，按下述目录形态组织（参考成熟的解读目录实践）：

```
{工作目录}/
├── README.md                # 顶层总索引（各技术分类 + 每个项目一行）
├── {模块}/                  # 按技术领域分类，如 auth/ IM/ rag/ devops/
│   ├── README.md            # 模块索引表：项目 | 语言 | 说明 | 协议 | 仓库
│   └── {项目}/
│       ├── README.md        # 项目解读主文档（`## 第X部分` 编号章节）
│       ├── 01-arch.md       # 可选：分层副文档（一个主题一篇）
│       └── arch.svg         # 可选：复杂架构图导出 SVG
```

- **主产出 = 项目解读页**（`{模块}/{项目}/README.md`），用 `## 第一部分` / `## 第二部分` 编号章节组织；内容过多时按主题拆成 `01-xxx.md` 副文档，README 内链接跳转。
- **模块归类**：按技术领域归类到对应 `{模块}/` 目录；不确定归入哪类、或需要新建分类时，向用户确认。
- **索引同步（收尾三步）**：建 `模块/项目/README.md` → 更新 `模块/README.md` 索引表 → 若模块尚不存在则新建分类并加入顶层 `README.md`。
- **Markdown 内部可渲染格式**（无需额外工具，GitHub / VS Code 即原生支持）：
  - 图表：` ```mermaid ` 代码块。
  - 对照 / 数据 / 清单：Markdown 表格。
  - 线性流程：ASCII 列表图（≤15 行）。
- **可选 SVG**：仅当遇到**大型或需定制视觉的复杂架构图**（节点多、需配色/标注/缩放）时，额外导出独立 `.svg` 文件，用 `![架构](arch.svg)` 嵌入同名目录的 md 中。**本 skill 不绑定任何特定的 SVG 生成 skill**——实现方式按效果自选，只保证产出是自包含、可离线打开、视觉清晰的 `.svg`。mermaid 代码块与 SVG **二选一**，不要为同一张图重复产出。
- **命名**：分层副文档 `01-xxx.md`、`02-xxx.md`；图文件与引用它的 md 同目录。

# 增量分析模式

对**已有解读文档**做更新或补充。**变更的唯一依据 = 上游 git diff / release notes**，禁止凭空重写或凭个人偏好重排。

## 铁律（违反即重来）

1. **先读现有文档，再动笔。** 不先读就改 = 失败。
2. **差异驱动。** 每处变更必须能追溯到上游 diff / release notes / 新增目录。找不到依据的改动不要做。
3. **确认覆盖范围。** 先定位现有文档已覆盖的内容，避免重复。先在仓库或上游核对**真实地址与版本**，拿到实际 release 变更或 git diff 作依据，而不是只信口头描述。
4. **最小破坏结构。** 已有编号章节（`## 第X部分`）原样保留，不移动、不删除、不重排标题。

## 变更粒度（从轻到重，够用就好）

1. **改段落** —— 更新"现状描述"里过时的数字/表述。
2. **加独立 md** —— 新增一个主题就新建 `xx.md`，别把 README 主体越堆越长。
3. **重排主体结构** —— 仅在确有必要时调整，几乎不该发生。

> 同一项目的版本演进优先**就地编辑 + 演进说明**，不要为它新建文件、破坏单文档强编号结构。

## 范围界定（什么值得写）

**值得写：** 影响"现状描述一致性"的数字（引擎数、默认库、接口数量）；新增的独立能力点；用户可感知的接入/用例变化。
**不值得写：** 为每个历史版本加脚注造成噪音；拆分新文件只为了不破坏结构；修改**竞品**行的描述（它不是本项目的组件）。

## 结构保护与演进标注

- 新增小节用 `###` 三级标题，与同部分兄弟小节平级，不进编号章节。
- 删掉的现状数字不直接抹掉，用 `> **演进说明(版本号)**` 引用块保留历史轨迹，再写新现状。
- 文档头更新版本号，并加一段"本版增量更新说明"，列出相比上一版的主要变更。
- 能力清单、技术栈表、架构图、对比表里的数字要**同步更新**，只改正文会漏。全篇 grep 核对一致性。

# 真源引用验证（Grounding）——防幻觉核心

解读文档里的引用要落地，核心是这一节。它保证阅读者点开的每一处论断都能对上真源码。

### 思想

模型给的行号是**猜的**，但模型从上下文**原样复制的 snippet 是可信指纹**。与其信行号，不如把 snippet 当线索去真实源码文件里搜索，算出真实行号。程序负责验证，不让模型自证。

### 关键约束（写进解读要求）

- 引用的 `snippet` 字段**必须从源码上下文逐字复制**，不得改写、不得凭记忆拼。
- 引用路径用**仓库相对路径 + 行号**，格式统一为 `模块/子目录/文件名.go:行号`，禁止使用裸文件名（如 `utils.go` 必须写成 `pkg/utils/util.go:42`）。
- 引用链接留空括号 `[path:start-end]()`，由程序统一补成真实 URL + 行锚点；落库前须经程序重定位，用真实行号覆盖模型给的行号。

### 核心实现（Python，可迁移，作为验证工具参考）

```python
# snippet 作为指纹，在真实源码里精确定位行号
def locate_snippet(text: str, snippet: str):
    snippet = snippet.strip("\n")
    if not snippet:
        return None
    pos = text.find(snippet)                       # ① 精确整段搜索
    if pos != -1:
        start = text.count("\n", 0, pos) + 1
        return start, start + snippet.count("\n")
    # ② 退化策略：以 snippet 首非空行为锚点
    first = next((ln.strip() for ln in snippet.splitlines() if ln.strip()), "")
    if first:
        idx = text.find(first)
        if idx != -1:
            start = text.count("\n", 0, idx) + 1
            return start, start + snippet.count("\n")
    return None

# 逐条重定位模型给出的引用
def ground_citations(citations, repo_dir):
    for cit in citations:
        if cit.start_line is None or not cit.snippet or not cit.file_path:
            continue
        path = os.path.join(repo_dir, cit.file_path)
        try:
            with open(path, "r", encoding="utf-8") as f:
                text = f.read()
        except OSError:
            continue
        loc = locate_snippet(text, cit.snippet)
        if loc:
            cit.start_line, cit.end_line = loc       # 真实行号覆盖模型行号
```

### 配套安全：读文件必须防路径穿越

```python
repo_dir = os.path.realpath(repo_dir)
target = os.path.realpath(os.path.join(repo_dir, file_path))
if os.path.commonpath([repo_dir, target]) != repo_dir:
    raise ValueError("Resolved path escapes the repository directory")
```

用 `realpath` 消除 `../` 与符号链接，再用 `commonpath` 确保目标仍在仓库根内——防止 `../../etc/passwd` 一类任意文件读取。

**教训**：若解读走 RAG（代码量大的仓库），切分时就要给每个 chunk 记录真实起始/结束行号（切分器对每个 chunk 独立复制 `meta_data`），否则后续落点无据可依。

# 写作规范（入库约定）

- 中文为主，技术术语保留英文（ForwardAuth、JWT、sqlc）。
- 代码块标注语言：`go`/`ts`/`yaml`/`sql`。
- 未完成章节用 `[WIP]`，待补充用 `TODO`；列表统一用 `-`。
- **代码引用统一为 `文件:行号` 且需经真源重定位验证**，禁止写记忆中的行号与路径。

# Mermaid 与图表约束（入库约定）

图表是解读的可视化支撑，但必须是"可渲染、可核对"的，不允许留下渲染报错的图。

**类型映射：**

| 图表用途 | Mermaid 类型 | 说明 |
|---------|-------------|------|
| 架构总览 | `graph TB` / `graph LR` | 模块层次、整体架构 |
| 流程图 / 启动流程 | `graph TB` | 步骤、请求链路、程序流程 |
| 时序图 | `sequenceDiagram` | 模块间交互、请求时序 |
| 状态图 | `stateDiagram-v2` | 状态流转、生命周期 |

**规模与原则：**

- 图谱控制在 **15 节点以内**，太复杂就拆成多个图，分别标注主题。
- 不追求面面俱到——抓关键链路，标注核心数据流方向。
- 线性流程（如启动流程）直接用 ≤15 行的列表式 ASCII 图，可读性更好。
- 落盘前**确认 Mermaid 语法可渲染**，不保留报错的图。

**与 SVG 的分工：**

- 默认用 md 内嵌的 ` ```mermaid ` 代码块（零成本，平台原生渲染）。
- 仅当需定制视觉 / 架构过大时，才导出独立 `.svg` 嵌入；同一张图不做 mermaid + svg 双份。

# 常见错误与对策

| 错误 | 修正 |
|------|------|
| 信任模型/记忆的行号 | 只信 verbatim snippet，程序在真实文件重定位真行号。 |
| 没先读现有文档就重写 | 增量铁律 1：先读。 |
| 凭感受大改结构 | 结构是资产，编号章节原样保留。 |
| 只改正文、漏掉能力清单/技术栈/图表里的数字 | 全篇 grep 核对所有出现处。 |
| 文档自称 v0.8 却没核对真实上游版本/diff | 增量铁律 3：先取真实依据。 |
| 新建文档后忘了更新模块索引 | 收尾三步不能跳。 |
| 把 README 翻译一遍充深度 | 这是提炼，不是翻译；深度不足标 [WIP]。 |
| 单文件暴力拼全部源码进提示词 | 超 token 且污染上下文；中小库打包相关文件，大库走 RAG。 |
| 引用用裸文件名不对应真实路径 | 一律仓库相对路径 `模块/子目录/文件.go:行号`，防穿越校验后落库。 |
| 引用无行号 | 引用须带真实行号，用 snippet 在真实文件重定位后补齐。 |
| 产出散落 / 忘建索引 | 产物就地落在执行工作目录的 `{模块}/{项目}/`，收尾三步更新模块与顶层 README。 |
| 图渲染报错或 mermaid+svg 重复 | 落盘前校验可渲染；同一张图只保留一种形式。 |
| 读源码文件无路径防护 | `realpath` + `commonpath` 白名单校验，防任意文件读取。 |
| 索引缓存永不失效 | 仓库更新后给旧内容；提供显式清除接口；cache 键含仓库+语言。 |

# Quick Reference

- 判断模式：项目分析目录**存在** → 增量；不存在 → 全新。
- 输入：本地源码绝对路径 → `repo_dir` 为验证根；远端先 clone；产出落执行工作目录。
- 输出：`{工作目录}/{模块}/{项目}/README.md` + `模块/README.md` 索引 + 顶层 `README.md`；主 md，可选 `01-*.md` 分层与 `.svg` 复杂图。
- 增量铁律：先读 → 差异驱动（git diff / release notes 为唯一依据）→ 最小破坏 → 同步数字与索引。
- 变更粒度：改段落 → 加独立 md → 重排主体（几乎不用）。
- 真源验证：snippet 是可信指纹，模型行号是猜的 → 在真实文件重定位覆盖；引用用仓库相对路径 `文件.go:行号` + 防穿越校验。
