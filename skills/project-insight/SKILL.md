# 开源项目洞察

## 核心理念

解读一个开源项目，产出的是**技术解构与提炼**，不是文档翻译或使用教程。每篇解读回答的根本问题：这个项目解决了什么、架构怎么组织、核心实现怎么落地、值得借鉴哪些模式、与同类相比的优劣势。

**落地场景：** 默认解读产物要落进一个持续维护的 Markdown 知识库仓库。因此约定目录结构、索引同步与写作风格，都是为了这批解读在该仓库内可长期检索、可随上游演进——为"解读入库"这一场景服务，不是为管文档而管文档。

**默认输出架构设计思路，不是编码细节。** 解读是对设计意图（Why>What、权衡、全局关联）的解构；类型定义、函数体、表结构等编码细节默认不整段贴出，仅在**用户主动要求深入某个实现**时才展开。判断"写成叙述还是贴码"的标准 = 这段是否承载了不可替代的设计观点：纯"字段是什么 / 这段逻辑怎么写的"一律压缩成一句叙述 + `文件:行号` 引用，让想深挖的用户自查源码，而非把完整函数体、大片 schema 复制进解读。

解读文档最大的敌人是**幻觉**——模型编造不存在的文件、行号、接口。因此必须坚守一条铁律：

> **让程序验证，不让模型自证。**

模型只负责产出**内容**；「这份论断是否真对得上源码」的判断，一律交给程序用确定性手段（子串匹配、路径校验、真实文件读取）去证实或纠正。文档里每个 `文件:行号` 引用，都必须能经程序重定位回真实源码，可点开验证。

**先判断模式，再动作。先读现状，后动笔。**

## 何时使用 / 何时不用

### 何时使用
- 知识库还没有某项目的解读 → **全新分析模式**
- 已解读项目上游发新版/重大变更 → **增量模式**
- 对已有解读觉得深度不足、再深入补充章节 → **增量模式**
- 要求解读必须**带可点开、可验证的真实源码引用**（文件路径+行号），避免幻觉

### 何时不用
- 翻译官方文档 / 写使用教程（本 skill 不做）。
- 项目专属约定（放项目的 instructions 文件，不进 skill）。
- 纯静态需求可枚举、无代码深挖场景，直接写死即可。

**临时分析判别：** 默认按"入库"规范执行（完整目录树 + 索引同步）。若用户只要一段临场解读、明确不落进知识库仓库，产出主体解读即可，并主动告知"本次未做索引同步、未做落地目录判定"；否则默认走完整入库流程（含下方 `kb_repo` 判定）。

## 输入

### 源码：本地绝对路径

默认输入是本地源码仓库的绝对路径，如 `/Users/me/src/wukong`：

1. 解析为统一 `source_repo`，用 `os.path.realpath` 规范化并确认存在，作为所有真源引用验证的根。
2. 用户只给远端地址（如 `github.com/xx/foo`）时，先 `git clone --depth=1` 浅克隆到本地再解读——真源验证必须读本地真实文件，不能对着远端记忆写；网络不可用则明确告知并请求本地路径。
3. 所有 `文件:行号` 引用以 `source_repo` 为根校验，防路径穿越。

### 落地目标：知识库仓库判定（自动 + 确认兜底）

产出目录**不默认等同于**执行时的当前工作目录，先做判定，确认后记为 `kb_repo`。

**目标结构模式：** `{分类}/{项目名}/README.md`（多关注面项目 + 主题式深读子文档），如 `IM/wukong/README.md`、`IM/wukong/architecture.md`。顶层 `README.md`（总索引）为加分项，非必要条件。

**判定信号（满足任一即视为"当前目录 = 目标知识库仓库"）：**
1. **结构扫描命中**：对当前目录深度为 2 扫描，存在至少一组 `{目录}/{目录}/README.md`，且该二级目录不是常见源码工程目录名（排除 `src`、`node_modules`、`cmd`、`internal`、`.git` 等，避免把源码仓库自身的 `pkg/utils/README.md` 误判为知识库结构）。
2. **显式索引命中**：顶层 `README.md` 内容含 `[分类](分类/README.md)` 或表格形式的模块索引链接。

**排除信号（命中即不匹配，禁止直接落地）：**
- 当前目录即本次 `source_repo` 或其子目录。
- 当前目录是具体编程项目源码根（存在 `package.json`/`go.mod`/`Cargo.toml` 等工程清单且无 md 知识库特征）。
- 当前目录为空且无任何 git/README 线索。

**执行逻辑：**
```
判定当前目录
├─ 命中判定信号 且 未命中排除信号 → 以当前目录为 kb_repo，落地
├─ 命中排除信号 → 停止，说明原因 → 走"用户选择"分支
└─ 两类信号都未命中（拿不准） → 展示目录树摘要 → 走"用户选择"分支
```

**用户选择分支（结构化二选一，不做开放式提问）：**

1. **指定其他目录** —— 用户提供已存在的知识库仓库绝对路径作 `kb_repo`；远端地址先 clone；不符合 `{分类}/{项目}/README.md` 结构则视为全新知识库仓库，按规范初始化。
2. **就在当前目录下新建** —— 以当前目录为 `kb_repo`，视为全新知识库仓库起点，按输出规范创建 `{分类}/{项目}/README.md` 并新建顶层 `README.md` 索引雏形。

示例确认话术：
> "当前目录 {cwd} 未检测到 `分类/项目/README.md` 这类知识库结构（原因：{具体原因}）。是否：① 指定一个已有知识库仓库路径 ② 就在当前目录 {cwd} 下新建这套知识库结构。请选择，或直接给出目标路径。"

> **特别提示：** 若由**排除信号**触发（如当前目录被识别为源码工程根），选项②不作为默认推荐，额外提示："注意：当前目录检测到 {go.mod/package.json 等}，看起来是代码仓库而非知识库仓库，在这里新建解读结构可能不是你要的，请确认。"

用户选定后记为 `kb_repo`，本次会话内模式判定、落地、索引同步均以此为根，不再重复询问。

## 模式判定

前提：`kb_repo` 已确认。

依据 `kb_repo/{分类}/{项目}/README.md` 是否已存在：

- 存在 → **增量模式**（必须先读现有文档再动笔）。
- 不存在 → 在 `kb_repo` 下按 `*/*/README.md` 全局扫描 + grep 项目名/仓库地址/别名，排除"已用别的分类名或别名建过索引"（如 wukong 被归到 `chat/` 而非 `IM/`）。
  - grep 命中 → 分类归属不一致导致的漏判，走增量模式，按命中位置定位真实文档，并询问是否顺带纠正分类归属。
  - grep 未命中 → 确认为全新项目，走全新分析模式。

# 全新的分析流程

新项目冷启动解读。

1. **确立根因先行**。读项目自述/README，一句写出"解决什么根本问题"。这是全篇的锚，防止写成功能罗列。
2. **规模门控（关键分流）**：估算有效代码行（剔除测试/构建/生成/示例代码）。
   - **超过 5 万行** → 转 [large-repo-workflow.md](references/large-repo-workflow.md) 的并行解读流程。
   - **未超过** → 继续本流程单 agent 执行。
3. **探索数据源（按序）**。README → 架构/设计文档 → 目录树（推模块划分）→ 核心模块代码 → 关键链路（启动流程 / 主请求链路）。其中在「目录树 → 核心模块代码」之间，必须对源码做一次 **数据模型探测**（见下方「数据模型主动探测」），命中即登记为候选数据模型关注面——这是流程里跑不掉的一步，不是凭「这项目像不像业务应用」的主观印象来决定。类型触发判据第 2 条（见「分文件判定」）是否命中，以此探测信号为准。
4. **定维度，非全覆盖**。从维度（概览/架构/认证/核心实现/存储/设计模式/部署/测试/社区/同类对比）里选项目特点最突出的 2-4 个深入，不要每个都写一段。
5. **写深，不翻译**。遵循 [analysis-guide.md](references/analysis-guide.md) 的深度方法论（Why>What、权衡、叙事连贯、全局关联、四要素完整性）。深度不足标 `[WIP]`/`TODO`，不硬凑。
6. **真源校验（不可跳过）**：
   - **代码引用**：对本次产出的全部 md 跑 `node scripts/verify-references.mjs <kb_repo> <产物.md>...` → 逐条重定位（有指纹块精确校验，无指纹块降级弱校验）→ `[GROUNDER-MISMATCH]` 用真实行号覆盖；`[GROUNDER-UNVERIFIED]` **保留原样并追加 `[UNVERIFIED]` 标记**，不静默通过，并在文末列出所有 `[UNVERIFIED]` 项提示人工复核；`[GROUNDER-TRAVERSAL]` 必须修复路径。退出码非 0 视为未通过。（`verify-references.mjs` 实现原理见「真源引用验证」。）
   - **Mermaid 图**：对本次产出的全部 md 跑 `scripts/check-mermaid.mjs` → 任一 `[MERMAID-ERROR]` 修复至全 `OK`，不保留渲染报错图（详见「图表约束」的 `### Mermaid 语法程序校验`）。
7. **维护索引（收尾三步）**：在 `kb_repo` 下创建 `{分类}/{项目}/README.md` → 更新 `{分类}/README.md` 索引表 → 若分类尚不存在，在 `kb_repo` 顶层 README 添加新分类。
8. **提交边界**：本 skill 只负责落盘（写文件、更新索引），**不自动执行 `git add/commit/push`**。若 `kb_repo` 是 git 仓库，落地后列出本次变更文件清单，提示用户自行决定是否提交，不代为决策。

## 文档结构

> **标题一律用 Markdown 天然层级，不加数字序号前缀。** 顶层 `##` 即最高章节，`###`/`####` 表达从属关系；不写 `## 1. X`、`## 0. X`、`## 第N部分：X` 这类数字前缀标题。并列列举如需在标题里体现顺序，用语义词（如 `## 决策一`、`### 亮点`、`### 问题`），而非纯数字前缀；列表项内部的 `.`/`-` 序号是列表，不算标题数字。

| 章节 | 内容 | 必选 |
|------|------|------|
| 快速概览 | 是什么 / 痛点 / 适用场景 / 核心能力清单表 / 技术栈一览表 | ✅ |
| 架构深读 | 架构总览图(Mermaid) / 启动流程 或 请求链路 / 模块职责映射(目录树) | ✅ |
| 按项目特点深入 | 核心实现 / 设计模式 / 部署 / 同类对比 / 数据模型 / 插件与 MCP / LLM 编排… | 可选 |

### 分文件判定（按项目复杂度/类型，不按代码量）

**拆分依据是"项目是否有多个可独立成文、且各自够深挖的关注面"，而不是代码行数或预计 README 体积。** 代码量大往往伴随关注面多，但行数只是复杂度的弱代理，最终以"关注面"为准：

- 项目可被自然切出 **≥3 个相对独立的关注面**（如数据模型、会话/记忆、Agent runtime、插件系统、MCP、LLM 编排、渠道接入、安全、部署……），且每个至少能展开一段有 `文件:行号` 佐证的深度内容，就**必须**为每个关注面独立成一篇子文档，README 只作索引/概览。
- **反向判断**：如果拆出来的子文档每篇都凑不够深度（没有可展开的 Why/权衡/源码佐证），说明是**为了拆而拆**，应退化为单文件。
- **关注面由"项目类型"驱动**：同一类型项目天然带同几类文档，遇之即拆、篇幅足够即独立成篇。类型触发判据见下方列表。

> **类型驱动的关注面触发判据**（满足即作为候选关注面；篇幅足够深挖则独立成 `xxx.md` 主题文档，浅则先并入 README 对应小节）：
>
> 1. **可部署项目**（Docker/常驻/云/安装器）→ 单独「部署文档」，覆盖 `docker-compose.yml` / `Dockerfile` / `systemd` / `launchd` / `fly.toml` / `render.yaml` 等形态与运维要点。
> 2. **有数据存储，或作为库/工具形态自带系统表与会话/元数据存储** → 单独「数据模型」文档：核心表/实体关系、存储选型与理由、Schema 演进策略（如 JSON blob + 提升列 / 迁移）、读写路径。文件名统一 `data-model.md`（存量文档如已用 `db-design.md` 则沿用原名，新文档一律 `data-model.md`）。**必含内容与写法见「数据模型文档规范」章节**（ER 图 + 每表字段表 / 存储选型 / 核心表设计 / 演进策略 / 读写路径）。注意：是否触发该判据由「数据模型主动探测」的程序化扫描信号决定，**不由「这项目是不是业务应用」的主观印象决定**——纯 library 框架只要自带系统表（如 go-admin 的 `goadmin_*`）、迁移（`migrations/`）、或 models 实体，同样属于数据模型关注面，须覆盖。
> 3. **有较长业务流程** → 用 `sequenceDiagram` 时序图体现完整业务链路（跨模块/跨服务的数据流、事件时序），而非只画单模块局部流；放在「架构深读」的请求链路节或单独 `flow-*.md`。
> 4. **智能体 (Agent) 相关** → 必须体现「记忆机制」：分层记忆（curated/episodic/prospective）、上下文压缩/compaction、检索策略、持久化。示例文件名 `memory-system.md` / `memory.md`。

**产出形态：** 中小/单一关注面项目 → 单文件 `README.md`；多关注面项目 → `README.md`（概览 + 架构总览 + 核心模块导读表 + 总结，每子文档一行链接）+ `xxx.md`（关注面深读，主题语义命名，一个主题一篇）。内容组合见下方 [丰富内容菜单](#丰富内容菜单)。

## 输出规范（入库约定）

产出以 **Markdown 为主**，落在已确认的 `kb_repo` 下，按此目录形态组织：

```
{kb_repo}/
├── README.md                # 顶层总索引（各技术分类 + 每项目一行）
├── {分类}/                  # 按技术领域分类，如 IM/ auth/ rag/ devops/
│   ├── README.md            # 分类索引表：项目 | 语言 | 说明 | 协议 | 仓库
│   └── {项目}/
│       ├── README.md        # 项目解读主文档（`##` 语义式章节）
│       ├── architecture.md │ 关注面子文档（多关注面项目必备，一个关注面一篇）
│       └── arch.svg         # 可选：复杂架构图导出 SVG
```

- **主产出 = 项目解读页**（`{分类}/{项目}/README.md`），用 `##` 语义式章节组织（不加数字前缀标题，见「文档结构」）；**多关注面项目必须按主题拆 `xxx.md` 子文档**，README 只承载 概览 / 架构总览 / 核心模块导读表 / 总结，深读放子文档，README 内链接跳转；禁止把全部内容压进单个 README。
- **README 子文档索引章节（强制，拆分即填）**：README 正文新增**一个独立章节**承载全部子文档索引，**一行一条**列出，格式：`- [\`xxx.md\`](xxx.md) — 一句话定位`。拆分/新增子文档必须同步回写此处，遗漏一项视为未完成。此章节是**全量子文档的总一览入口**；正文各章节、导读表每一行还需按下文「README 正文导航」就近给出内链，两处互补、共同构成读者入口。多关注面项目 README 结构模板：
  ```
  # 标题

  ## 子文档索引

  - [`architecture.md`](architecture.md) — 架构总览与协议
  - [`memory-system.md`](memory-system.md) — 记忆系统 …
  （逐个列出全部子文档）
  ```
- **README 正文导航（强制，与「子文档索引」章节互补）**：独立「子文档索引」章节负责"一览全部子文档"，README **正文**则负责"按阅读路径就近跳转"——「核心模块导读表」每一行都用 `[\`xxx.md\`](xxx.md)` 链接到对应子文档；概览 / 架构总览 / 总结章节中提到某一关注面时，同样就地给出 `[\`xxx.md\`](xxx.md)` 内链。两处不可互相替代：导读表每行可点超链是读者顺着模块点击深读的主入口，遗漏一个行内链接即视为该关注面入口缺失。
- **分类归属**：按技术领域归类到对应 `{分类}/`；不确定或需新建分类时向用户确认。
- **索引同步（收尾三步）**：建 `{分类}/{项目}/README.md` → 更新 `{分类}/README.md` 索引表 → 若分类不存在则新建并加入顶层 `README.md`。
- **可渲染格式**（无需额外工具，GitHub / VS Code 原生支持）：
  - 图表：` ```mermaid ` 代码块。
  - 对照/数据/清单：Markdown 表格。
  - 线性流程：ASCII 列表图（过长收束为关键步骤）。
- **可选 SVG**：仅遇到大型或需定制视觉的复杂架构图（节点多、需配色/标注/缩放）时额外导出独立 `.svg`，用 `![架构](arch.svg)` 嵌入同目录 md。不绑定特定 SVG 生成 skill，实现方式按效果自选，只保证自包含、可离线打开、视觉清晰。mermaid 与 SVG **二选一**，不要重复产出。
- **命名**：子文档**统一主题语义命名**（如 `architecture.md`、`deployment.md`、`data-model.md`、`memory-system.md`、`llm-route-system.md`），**不用 `01-`/`02-` 序号前缀**（个别存量项目的历史编号式命名不沿用）；图与引用它的 md 同目录。

# 增量分析模式

对**已有解读文档**做更新或补充。**变更的唯一依据 = 上游 git diff / release notes**，禁止凭空重写或凭偏好重排。拿不到 git diff / release notes（本地仓库无 `.git` 历史、上游未写 changelog）时退化为**代码快照比对**：对比当前代码与既有文档描述差异，并在文中显式声明"本次依据代码快照比对，非官方 changelog"。

## 铁律（违反即重来）

1. **先读现有文档，再动笔。** 不先读就改 = 失败。
2. **差异驱动。** 每处变更必须能追溯到上游 diff / release notes（或声明的代码快照比对）。找不到依据的改动不做。
3. **确认覆盖范围。** 先定位现有文档已覆盖内容，避免重复；先在仓库或上游核对**真实地址与版本**，取实际 release 变更或 git diff 为依据，不只听口头描述。
4. **最小破坏结构。** 已有 `##` 章节标题原样保留，不移动、不删除、不重排标题。

## 变更粒度（从轻到重，够用就好）

1. **改段落** —— 更新"现状描述"里过时的数字/表述。
2. **加独立 md** —— 新增一个主题就新建 `xx.md`，别把 README 主体越堆越长。
3. **重排主体结构** —— 仅在确有必要时，几乎不该发生。

> 同一项目的版本演进优先**就地编辑 + 演进说明**，不为此新建文件、不破坏单文档强编号结构。

## 范围界定（什么值得写）

**值得写：** 影响"现状描述一致性"的数字（引擎数、默认库、接口数量）；新增的独立能力点；用户可感知的接入/用例变化。
**不值得写：** 为每个历史版本加脚注造成噪音；拆分新文件只为了不破坏结构；修改**竞品**行描述（它不是本项目组件）。

## 结构保护与演进标注

- 新增小节用 `###` 三级标题，与同部分兄弟小节平级，不挤进顶层 `##` 章节层级。
- 删掉的现状数字不直接抹掉，用 `> **演进说明(版本号)**` 引用块保留历史轨迹，再写新现状。
- 文档头更新版本号，加一段"本版增量更新说明"，列出相比上一版的主要变更。
- 能力清单、技术栈表、架构图、对比表里的数字要**同步更新**，只改正文会漏。全篇 grep 核对一致性。
- 同全新分析流程真源校验：改完后重跑一遍 `scripts/verify-references.mjs` 与 `scripts/check-mermaid.mjs`，新增/改动的引用同样经程序重定位，失败标 `[UNVERIFIED]`；`[MERMAID-ERROR]` 修复至全 `OK`。
- 落盘后同样只提示变更清单，不代为 `git commit`。

# 真源引用验证（Grounding）——防幻觉核心

解读里的引用要落地，核心在这一节。它保证阅读者点开的每处论断都对得上真源码。

### 思想

模型给的行号是**猜的**，但从上下文**原样复制的 snippet 是可信指纹**。与其信行号，不如把 snippet 当线索去真实源码里搜索，算出真实行号。程序负责验证，不让模型自证。

### 关键约束（写进解读要求）

- 引用的 `snippet` 字段**必须从源码上下文逐字复制**，不得改写、不得凭记忆拼。**它是内部定位指纹，不是文档展示内容。**
- 引用路径用**仓库相对路径 + 行号**，格式统一为 `模块/子目录/文件名.ext:行号`（后缀按项目语言替换，如 `.ts`/`.py`/`.rs`）；禁止裸文件名（`utils.go` 必须写成 `pkg/utils/util.go:42`）。
- 引用链接留空括号 `[path:start-end]()`，由程序统一补成真实 URL + 行锚点；落库前须经程序重定位，用真实行号覆盖模型行号。
- **定位失败不允许静默放过**：找不到匹配的引用必须保留原样并追加 `[UNVERIFIED]` 标记，在文末汇总列出，交由人工复核，不能与已验证引用长得一样。

> **引用展示与指纹分离（防"正文贴码"）**：`snippet` 只在程序内做真实源码重定位，**默认不进入文档正文**。正文里每处引用统一呈现为「一句结论/权衡/叙述 + `[路径:start-end]` 标点」，不复制整段代码：
>
> ```
> Gateway 把"连接为什么失败"变成可观测：close 时把 `closeCause`/`phase`/`lastFrameType` 全部带进日志 close context（`src/gateway/server/ws-connection.ts:486-505`）。
> ```
>
> 完整实现细节交给读者点开 `[路径:start-end]` 的源码锚点即可。仅当 **该段代码本身就是不可绕过的设计载体**，且用户明确要求贴码时，才允许放**精简片段**（只取不可绕过的核心，不整段照搬），孤立的 `> [path] — 整段代码` 引用块列为违规。

> **指纹块（Grounding fingerprint）约定**：为使程序精确校验行号，每条展示引用 `[path:start-end]()` 后应紧邻一个**不进入正文渲染**的指纹注释（常规做法，非可省略项；省略时脚本只能降级弱校验，无法发现行号偏差）。两种形式二选一：
>
> ```
> [path:start-end]() 一句结论/权衡
> <!-- snippet: 从源码逐字复制的片段（仅作程序定位用，不进正文） -->
>
> <!-- 或 base64 形式（snippet 含 `--` 等破坏注释的字符时用）：
> <!-- snippet-base64:<snippet 原文的 base64> -->
> ```
>
> - snippet 必须**从源码上下文逐字复制**（上述铁律不变），只作程序重定位用、不进入正文。
> - 程序读取该注释 → 在真实源码里整段搜索 → 算出真实行号 → 校对文档标注，输出 `[GROUNDER-OK/MISMATCH]`。
> - 定位失败时脚本输出 `[GROUNDER-UNVERIFIED]`，与正文标 `[UNVERIFIED]` 对应，文末汇总供人工复核。

### 核心实现（已有可运行工具，原理简述）

> 真源重定位已由 `scripts/verify-references.mjs` 落地（`node verify-references.mjs <kb_repo> <解读.md>...`），输出 `[GROUNDER-OK/WEAK/MISMATCH/UNVERIFIED/TRAVERSAL]` 五态并控制退出码，内嵌路径防穿越。核心原理如下（跨语言可迁移，脚本即按此实现）：
>
> - **定位**：snippet 是可信指纹——`text.find(snippet)` 精确整段搜索定位真实行号；失败则退化到"以 snippet 首非空行为锚点"搜索。
> - **覆盖**：定位成功用真实行号覆盖模型行号；失败显式置为未验证（对应 `[UNVERIFIED]`），不静默放过。
> - **防穿越**：`realpath` 消除 `../` 与符号链接，再校验目标仍在仓库根内（`commonpath`/公共前缀）——防止 `../../etc/passwd` 一类任意文件读取。此校验同样适用于对 `kb_repo` 的任何读写。

**教训**：若解读走 RAG（代码量大的仓库），切分时给每个 chunk 记录真实起始/结束行号（切分器对每个 chunk 独立复制 `meta_data`），否则后续落点无据可依。

# 写作规范（入库约定）

- **中文为主，术语/标识符保留英文**（ForwardAuth、JWT、sqlc、类型/字段/变量名、命令）。正文一律中文；引用**非中文原始片段**（官方文档原话、README 引文等）时：优先用中文转述核心论断；确需保留英文原句的，**必须紧跟一段中文解读**，禁止出现孤立无解读的整段英文。检验标准：一个不读源码的阅读者只看中文也能理解每个论断的设计含义。
- 代码块标注语言：`go`/`ts`/`yaml`/`sql`。
- 未完成章节用 `[WIP]`，待补充用 `TODO`；列表统一用 `-`。
- **代码引用统一为 `文件:行号` 且须经真源重定位验证**，禁止写记忆中的行号与路径；定位失败一律标 `[UNVERIFIED]`。
- 深度标准遵循 [analysis-guide.md](references/analysis-guide.md)：每个关键论断带 Why、权衡与对比，避免泛泛而谈。

### 阅读体验配额（结构护栏）

**篇幅决定权交给"关注面与深度"，不设任何行数上限。** 主 `README.md` 是概览 + 导读，深度内容按关注面拆进子文档（见「分文件判定」）；因此篇幅天然由项目复杂度驱动——单关注面小项目一页即够，多关注面大项目 README + 若干子文档各说各话，不为达标而压缩有效内容、也不为凑篇幅硬填。

**篇幅自查以"该拆已拆、无拖沓"为准：** 超常规篇幅先自查——是否把多关注面硬塞进了单个 README（应拆子文档）、是否有可压缩的拖沓；若拆分已合理、每段都承载设计纵深，篇幅长是合理的。反过来，单关注面项目篇幅短正常，**不必硬凑**。

**内容配额（比篇幅更难、更需要纪律，这是真正的强制项）：**

- **代码引用只作"依据"，不作"素材"**：正文每处引用自带一句结论/权衡/叙述 + `[路径:行号]` 标点，**不内嵌整段代码**（格式与理由见「真源引用验证」一节）。非-mermaid 代码块**数量以传达设计为准，不追求凑数**，仅保留真正承载设计的关键类型/接口（精简片段，不整段贴实现）。
- **文字能用图替就替**：启动流程、核心请求链路、连接/会话生命周期、跨模块时序，命中即用 `sequenceDiagram`/`graph`（见「图表约束」强制清单），禁止纯文字长段描述过程。
- **信息密度优先**：能成表的转表格，能成图转图，能用一句理由说明就不铺三句；"泛泛而谈"比"缺内容"更严重。

# 图表约束（入库约定）

图表是解读的可视化支撑，必须"可渲染、可核对"，不允许留下渲染报错的图。**「可渲染」不是靠模型自我断言，而是落盘前跑程序校验（见下方 `### Mermaid 语法程序校验`）。**

**类型映射：**

| 图表用途 | Mermaid 类型 | 说明 |
|---------|-------------|------|
| 架构总览 | `graph TB` / `graph LR` | 模块层次、整体架构 |
| 流程图 / 启动流程 | `graph TB` | 步骤、请求链路、程序流程 |
| 时序图 | `sequenceDiagram` | 模块间交互、请求时序 |
| 状态图 | `stateDiagram-v2` | 状态流转、生命周期 |

**规模与原则：**

- 图谱以保证可读性为准：过于复杂就拆成多个图分别标注主题，不因贪图单图完整而牺牲可读性。
- 不追求面面俱到——抓关键链路，标注核心数据流方向。
- 线性流程（如启动流程）直接用列表式 ASCII 图，过长则收束为关键步骤。
- 落盘前对本 skill 产出的所有 mermaid 块跑一遍 `scripts/check-mermaid.mjs`（见下方校验节），有 `[MERMAID-ERROR]` 必须先修复再落盘，不保留渲染报错的图；`<br>` 换行的 `[MERMAID-WARN]` 也应收敛为 0，避免长标签在预览下挤压。可渲染与否是**程序判定**，不是「模型认为没问题」。

### Mermaid 语法程序校验

沿用「让程序验证，不让模型自证」的铁律：mermaid 是否可渲染，交给真实解析器判定，而不是模型自查。本 skill 提供可运行校验脚本 `scripts/check-mermaid.mjs`，用 `mermaid.parse()` 真解析 Markdown 里的每个 ` ```mermaid ` 块（flowchart / sequenceDiagram / stateDiagram-v2 / 其他支持的类型都覆盖）：

- **依赖与准备**：脚本目录 `scripts/` 需要 `mermaid` 与 `jsdom` 两个依赖，首次使用在 `scripts/` 下执行 `npm install` 一次即可（`node_modules` 已 gitignore，不随仓库提交；若本机 skill 是**复制**注册而非软链到本仓，复制后需在 `scripts/` 重新 `npm install`）。
- **调用**：`node scripts/check-mermaid.mjs <解读文件.md> [file2.md ...]`（不传参数时从 stdin 读）。建议把本 skill 本次产出涉及的全部 md 一次性传入。
- **输出与判定**：逐块打印 `OK  [文件:全局起止行] type=图类型`，或 `[MERMAID-ERROR] [文件:行区间]` + 具体报错位置（含换算到文件的全局行号）与解析详情。任一 `[MERMAID-ERROR]` → 进程退出码非 0。
- **`<br>` 换行规范性检查（提示级）**：除语法解析外，脚本还对所有 ` ```mermaid ` 块做 `<br>` 专项 lint，输出 `[MERMAID-WARN]`（不计入非 0 退出码，仅打印提示，避免误伤合法图）。三条规则：① 换行统一用无斜杠的 `<br>`（mermaid 官方文档与 HTML 主流写法），检测 `<br/>`/`<br />`/`</br>` 等带斜杠形式并提示统一为 `<br>`；② `<br>` 只应出现在引号包裹的节点标签内，edge/`message` 等裸文本行的 `<br>` 不被当作标签换行处理，予以提示；③ 标签被 `<br>` 切开后单段仍超 40 字符（或整段无换行超 40 字符）时，提示在语义断点再补 `<br>`，以改善预览可读性。产出中凡用到 `<br>` 的图，应让脚本的 `[MERMAID-WARN]` 收敛为 0。
- **失败处理（不静默放过）**：有 `[MERMAID-ERROR]` 时，必须定位到报错块、按真实解析器给出的位置修复，改完重跑直到全 `OK`。这与真源引用定位失败的 `[UNVERIFIED]` 同理——不允许把渲染报错的图当作已完成交付。
- 本脚本是**校验工具**，不是产出物；它只读、不改动解读文档。

**强制图位清单（命中即必须给图，禁止纯文字长段走流程）：**

| 触发 | 必给图 |
|------|--------|
| 架构总览 | `graph TB/LR` 模块图 |
| 启动流程 / 主请求链路 | `sequenceDiagram` 或 `graph` 阶段图 |
| 连接 / 会话生命周期 | `stateDiagram-v2` 或 `sequenceDiagram` |
| 跨模块数据流 / 时序 | `sequenceDiagram` |

- 子文档每篇**至少 1 张**属于本关注面的核心链路图（README 的架构总览图不重复计入）。
- 图是读懂过程的主体，旁注文字只做图外补叙与权衡说明。

**与 SVG 分工：**

- 默认用 ` ```mermaid ` 代码块（零成本，平台原生渲染）。
- 仅需定制视觉/架构过大时才导出独立 `.svg` 嵌入；同一张图不做双份。

# 数据模型文档规范

判定依据见「分文件判定」类型触发判据第 2 条：**项目有数据存储，或作为库/框架自带系统表与会话/元数据存储**（关系库 / NoSQL / 键值 / 文件式数据）即必须产出数据模型文档，独立成篇时命名统一 `data-model.md`（存量 `db-design.md` 沿用原名，新文档一律 `data-model.md`）。数据模型是"关注面"中最容易退化成"字段清单罗列"的一类——本小节与其说是补内容，不如说是**强制把它写成设计，而非数据字典**。判断标准：一个读者看完能回答"为什么用这套存储、数据怎么演进、写读路径怎么走"，而不是只看到一张表。

**是否进入本关注面，由下方「数据模型主动探测」的程序化扫描决定，不由"这项目是不是业务应用"的主观印象决定。**

### 数据模型主动探测（流程内强制一步）

在探索阶段（见「全新的分析流程」step 3）对本源跑一次**确定性信号扫描**，任一命中即登记为候选数据模型关注面，再按下方五要素成文；全部未命中才可判定无此关注面：

- **文件形态**：glob `**/*.sql`、`**/migrations*/`、`**/schema*/`；含 `CREATE TABLE` 的迁移/建表脚本。
- **语言/ORM 约定**：`models/`、`entities/`、`domain/` 目录；（Node）`*.prisma`；（Python）`alembic/versions*`、`models.py`；（Go）ORM `Sync2`/`AutoMigrate` 建表入口（本项目用 `xorm.io/xorm` 的在 `engine` 或插件 `InitPlugin` 处建系统表）。
- **会话/元数据存储**：会话、配置、操作日志等非业务表的持久化定义（如 `goadmin_session`、`goadmin_operation_log`）。
- 库/框架型项目自带 `goadmin_*` 系统表、`data/migrations/`、models 实体即命中，**不得因"自带而非业务应用"跳过**。

> 触发示例（go-admin）：探测命中 `data/migrations/`（`admin_YYYY_MM_DD_..._{mysql,postgres,sqlite,ms}.sql` 8 个按库分文件）、`plugins/admin/models/`（`base/menu/operation_log/permission/role/site/user.go` 7 个模型）、`plugins/admin/data/mysql/admin.sql`（`admin.sql:28/64/84/113/141/167/192/219/235/260` 定义 10 张 `goadmin_*` 表）→ 应产出 `data-model.md`，而非让表只散落在 table-dsl / auth-rbac 里。

命中且篇幅足够独立深挖则单独成篇 `data-model.md`；篇幅偏浅可先并入 README 对应小节，但**必须**至少有 ER 图 + 核心表字段表 + 一句存储选型理由，不得整段省略。

数据模型文档**必含**以下五部分（缺一部分即未完成）：

> **必含清单（成文时二者皆需）：** Mermaid `erDiagram`（或 `graph`）实体关系总览图 + **每张核心表一个 Markdown 字段表**（`字段 | 类型 | 约束 | 说明`）。ER 图承担"有哪些实体、怎么关联"，字段表承担"每张表有哪些字段、约束如何"，缺图或缺表均视为未完整交付。

### 实体关系总览

优先用 Mermaid `erDiagram` 画实体/表及其关系（一对多、多对多经中间表等）；不适用 `erDiagram` 的场景（文档型 / 键值型）用 `graph TB` 表达实体集合与引用。同受「图表约束」的 `check-mermaid.mjs` 程序校验，落盘前全 `OK`。关系图是本节主体，文字只做图外补叙与权衡说明。

### 存储选型与理由

说清**为什么选这套存储**，而不是罗列用了什么：关系型 vs 文档型 vs 键值型的权衡、一致性/可用性/分区三种取向、对比不选方案的代价。这是数据模型的"根因"，也是最体现设计深度的部分。

### 核心表 / 实体设计

ER 图只表达了"有哪些表、怎么关联"，还缺字段级信息。因此**对每张核心表**都配一个 Markdown 字段表，作为 ER 图之外的结构化补充——这正是"ER 图 + 表格形式数据表说明"的组合：

| 字段 | 类型 | 约束（主/外键、索引、非空、默认） | 说明 |
|------|------|--------------------------------------|------|

- 每表一张字段表，紧随该表在 ER 图中的表述或其后集中列出；表头前用**一句叙述**说清该表职责，并用 `文件:行号` 指向实际 schema / 实体定义。
- 字段表是"更结构化的叙述"，不是把建表 SQL 原样照搬：字段、类型、主外键、索引、默认值以**表格字段**呈现，行序按设计要点而非建表语句顺序，另配"说明"列写该字段承载的设计取舍与关联。
- 贴码克制铁律沿用（见「真源引用验证」引用展示与指纹分离）：**仍不整段复制建表 SQL / 类型定义块**；每张表的精确字段改由字段表 + `文件:行号` 提供，读者可点开真实 schema 复核。仅当某字段或索引结构本身就是不可绕过的设计载体时才放精简片段。

### Schema 演进策略

数据怎么随版本演进：迁移机制（migration 工具 / 手动 DDL）、JSON blob + 提升列的渐进式加字段、向后兼容与读写双写、灰度与回滚。没有迁移层时也要说明当前如何保证演进安全。

### 读写路径

数据从写入到读取的关键链路（谁写、何时写、谁读、经什么中间层）。命中「图表约束」强制图位即用 `sequenceDiagram` 承载时序，标注关键 `文件:行号`，文字只做图外补叙。

> **与上下文的全局关联（沿用「写作规范」全局关联铁律）：** 数据模型不是孤立的表清单——每类数据都要连回它服务哪个业务能力、支撑哪条请求链路，与 README 概览、架构总览、其他子文档间保留过渡句。

# Quick Reference

- 判断落地目标：先扫描当前目录是否符合 `分类/项目/README.md` 结构 → 符合则直接用；命中排除信号或拿不准 → 结构化二选一（指定新目录 / 就在当前目录新建），确认后记为 `kb_repo`。
- 判断模式：`kb_repo/分类/项目/README.md` **存在** → 增量；不存在（且 grep 无别名命中）→ 全新。
- 规模分流（**解读执行的并行门控**，与输出分文件是两件事）：估算有效代码行，**>5 万行** → [large-repo-workflow.md](references/large-repo-workflow.md) 并行流程；否则单 agent。
- 输入：本地源码绝对路径 → `source_repo` 为验证根；远端先浅克隆；`kb_repo` 同理支持远端。
- 输出：`{kb_repo}/{分类}/{项目}/README.md` + `{分类}/README.md` 索引 + 顶层 `README.md`；主 md + 必要主题式 `xxx.md` 深读子文档 + `.svg` 复杂图。
- 分文件（**输出落盘判据**，按项目复杂度/类型非行数）：项目可自然切出 ≥3 个能独立深挖的关注面（或命中类型触发判据）→ 必须拆子文档，README 只做概览/导读，深读进子文档；凑不够深度则退化为单文件。
- 深度：遵循 [analysis-guide.md](references/analysis-guide.md)——Why>What、权衡三角、对比式思考、叙事连贯、全局关联、四要素可复现性。
- 阅读体验：篇幅由关注面驱动、不设上限；引用展示与指纹分离、强制图位、子文档索引三约定，详见「阅读体验配额 / 图表约束 / 分文件判定」。
- 增量铁律：先读 → 差异驱动（git diff / release notes 为唯一依据，拿不到则声明代码快照比对）→ 最小破坏 → 同步数字与索引。
- 变更粒度：改段落 → 加独立 md → 重排主体（几乎不用）。
- 真源验证：`verify-references.mjs <kb_repo> <解读.md>...` 程序重定位，snippet 只作定位不进正文，失败标 `[UNVERIFIED]`，引用用仓库相对路径 + 防穿越校验。
- 图表：Mermaid ` ```mermaid ` 为主（落盘前跑 `scripts/check-mermaid.mjs` 校验全 `OK`；`<br>` 换行统一 `<br>`、`[MERMAID-WARN]` 收敛为 0），超大/定制视觉才导 `.svg`，不重复；启动/请求链路/生命周期/跨模块时序强制给图。
- 收尾（全新）：建项目 README → 更新分类索引 → 必要时顶层 README → 列变更清单，不代为 commit。
- 质量红线：kb_repo 判定 / 能力表 / 技术栈表 / Mermaid 图（`check-mermaid.mjs` 全 OK）/ 链路 / ≥2 处真源引用 / 根因 / 深度达标（四要素）/ 正文无整段贴码 / 语义式标题（无数字前缀）/ 中文为主 + 英文必配解读 / 索引同步 / 引用程序验证（`verify-references.mjs` 全过 + UNVERIFIED 标记）/ 图表可渲染（程序判定）。
