# Design Doc（技术方案 / 设计文档生成器）

编写一份「方案类技术文档」并落盘。核心是**先澄清、再定档、按类型裁剪、守质量红线**，避免一上来就套大模板产出又长又不贴题的文档。

## 与其它技能的边界

- 文档内需要配图 → 用 Mermaid 内嵌（规范见 `references/quality-bar.md`）。
- 用户只要**独立 SVG 图表文件**（可离线打开的架构图/拓扑图交付物）→ 改用 `svg-maker`，本 skill 不生成。
- 深度解读开源项目源码 / Git 操作 → 分别走 `project-insight` / `git-kit`。

## 工作流程

1. **澄清**（信息不足时，最多问 3 个问题：使用场景、目标受众、技术栈与约束）。
2. **定复杂度** → 选模板档（读 `references/templates.md`）。
3. **定类型** → 取裁剪与补充清单（读 `references/types.md`）。
4. **撰写** → 全程守 `references/quality-bar.md` 的质量红线（图/代码/措辞/清单）。
5. **落盘收尾** → 按 `references/output.md`（命名、存储、校验、报告）。

### 复杂度分级（决定模板档位）

| 档位 | 适用 | 判定信号 | 对应模板 |
|------|------|----------|----------|
| 轻量 | 单个功能/模块、小型优化、简单集成 | 改动面小、影响一个模块、一次评审能过 | `templates.md` 轻量档 |
| 标准 | 子系统、中型业务模块 | 跨多个模块/服务、含数据与接口设计 | `templates.md` 标准档 |
| 完整 | 系统架构、跨系统集成、技术重构、大型平台 | 全链路评估，需覆盖性能/容量/安全/成本 | `templates.md` 完整档 |

**原则：宁轻勿重。** 拿不准就先用轻量档，靠类型清单或明确需求再往上加章节——避免过度设计。

### 方案类型（决定重心与可裁剪章节）

| 类型 | 命中信号（举例） | 详见 |
|------|----------------|------|
| 通用（默认） | 未命中以下任一类型 | `types.md` |
| 架构设计 | 系统架构、微服务拆分、模块化、跨系统集成 | `types.md` |
| API 设计 | 接口定义、REST/RPC/gRPC、OpenAPI | `types.md` |
| 数据模型设计 | 数据库设计、ER、分库分表、索引 | `types.md` |
| 性能优化 | 瓶颈、QPS/RT、缓存、压测、高并发 | `types.md` |
| 安全方案 | 认证授权、数据加密、威胁建模 | `types.md` |

类型**不改变档位**：模板决定章节骨架与篇幅，类型决定「加深哪几节、加哪些类型特有要点、可删哪几节」。冲突时以类型清单为准，并在文档里说明取舍理由。

### 按需加载

| 当下需要 | 读取 |
|----------|------|
| 正文骨架 | `references/templates.md` |
| 按类型裁剪/补充 | `references/types.md` |
| Mermaid 图、代码片段、论证、评审清单、措辞 | `references/quality-bar.md` |

只读当前所需小节，不整篇搬运。

## 收尾铁律

1. 用 `write` 完整落盘，**确认写入成功**后再做下一步。
2. 报告生成路径（格式见 `references/output.md`）；**不擅自执行 `code` 打开文件**——当前宿主（dsh Web）无此语义。仅当用户明确要求、且本机确有对应编辑器时才尝试，失败即提示手动打开。
3. 文档含 Mermaid 图且本机能定位到本 skill 目录时，跑校验：
   `node <本skill目录>/scripts/check-mermaid.mjs <生成文件>`
   `[MERMAID-ERROR]` 必须修复后重跑，**不静默放过**。
4. 按复杂度档位生成评审检查清单（真源见 `references/quality-bar.md`），轻量档 5-8 条、标准/完整档相应加量并叠类型特有项。
5. 落盘后不做 git add/commit（是否纳入版本管理由用户决定）。

## 注意事项

- 避免过度设计：贴合实际业务规模，小需求不套企业级章节（成本/容灾/压测等）。
- 强调可落地：考虑团队技术栈、运维能力等现实约束。
- 提供对比分析：技术选型给 2-3 种方案及取舍理由。
- 注重可读性：非技术人员也能读懂核心思路。
- 保持中立：选型客观分析优劣，不带偏见。
