# Tech Design（技术方案 / 技术设计文档）

写一份**能被评审、能被执行**的方案文档：先澄清规模与约束 → 定篇幅档位 → 定变更场景 → 选专题加固 → 量化关键论断 → 落盘并自检。

三条贯穿全文的硬要求：

1. **量化义务**：凡涉及性能、容量、可用性、成本、规模的论断，必须给数字或区间 + 口径 + 假设来源；给不出就显式标为「待验证假设」并写清不成立时的应对，不允许用形容词代替（见 `references/quantification.md`）。
2. **取舍对偶**：每个关键选型必须回答「为什么选它 / 代价是什么 / 什么情况下不该选它」；只讲优点、或只给一个方案的对比视为未完成。
3. **宁轻勿重**：档位从低起步，出现明确信号才上浮；骨架是覆盖清单而非填空卷——不适用的章节**删掉**，不留 "N/A" 或一句话占位。

## 与其它技能的边界

- 文档内配图 → Mermaid 内嵌（规范见 `references/quality-bar.md`）。
- 用户只要**独立 SVG 图表文件** → 改用 `svg-maker`。
- 深度解读开源项目源码 / Git 操作 → 分别走 `project-insight` / `git-kit`。

## 工作流

1. **澄清** → 按下表优先级最多问 3 个问题，其余落成显式假设。
2. **定档** → 三档篇幅/评审范围（`references/templates.md`）。
3. **定场景** → 单选：新建 / 增量改造 / 结构重构 / 替换与迁移 / 下线与废弃 / 专项优化（`references/scenarios.md`）。
4. **选专题** → 可多选加固方向（`references/focus-areas.md`）。
5. **量化** → 关键论断的数字与口径（`references/quantification.md`），与撰写同步做。
6. **撰写** → 全程守 `references/quality-bar.md` 的红线与反模式。
7. **自检 → 落盘 → 报告** → 见「交付与收尾」。

### 澄清问题清单（按优先级取前 3 个）

只问**决定文档结构的问题**，不问能从代码或用户原话里推出来的问题。

| 优先级 | 问题 | 为什么必须问 |
|--------|------|--------------|
| 1 | 规模量级：多少用户/多少数据/多大 QPS 或读写比？ | 没有规模既无法定轻重，也无法量化 |
| 2 | 改动范围：从零新建、在既有系统上改动，还是替换/下线既有能力？涉及哪些上下游？ | **答案直接决定场景**（过程义务、章节增删），见 `references/scenarios.md` |
| 3 | 硬约束：技术栈、部署环境、可用性/延迟/合规要求、排期与人手？ | 决定选型边界与非目标 |

用户答不上来时**不阻塞**：给一个明确默认值，写进文档「假设与约束」并标注待确认。

### 定档（决定篇幅与评审范围）

| 档位 | 适用 | 判定信号 | 骨架 |
|------|------|----------|------|
| 轻量 | 单模块功能、小型优化、简单集成 | 改动面小、一次评审能过、无跨系统影响 | `templates.md` 轻量档 |
| 标准 | 子系统、中型业务模块 | 跨多个模块/服务，含数据与接口设计 | `templates.md` 标准档 |
| 完整 | 系统架构、跨系统集成、重构/迁移、大型平台 | 全链路评估，含容量/安全/成本/回滚 | `templates.md` 完整档 |

拿不准先用轻量档；出现这些信号才上浮：跨团队评审、SLA 承诺、成本敏感、合规审查、不可逆变更。场景与档位的常配关系见 `references/scenarios.md` 速览表。

### 定场景（决定叙事起点与过程义务，单选）

| 场景 | 一句话判定 |
|------|------------|
| 新建 | 从零做，无存量（删现状类章节） |
| 增量改造 | 改或加既有功能，行为改变（要影响面 + 兼容性 + 回归范围） |
| 结构重构 | 结构变、行为应不变（要行为基线 + 等价性验证 + 切流回滚） |
| 替换与迁移 | 换存储/中间件/框架/供应商（要能力差异清单 + 对账 + 回退窗口） |
| 下线与废弃 | 移除既有能力（要消费者盘点 + 下线判据 + 数据处置） |
| 专项优化 | 结构不变、只冲指标（要指标基线 + 回归范围 + 收益代价） |

同时命中多个时取**风险更高、过程更长**者为主场景，另一场景的必答项作为补充义务并入。判定顺序、必答项、章节增删、验收与回滚形态见 `references/scenarios.md`。

### 选专题（决定加深哪几节，可多选）

**架构设计 / API 设计 / 数据模型设计 / 性能与容量 / 安全 / 迁移手法**（无命中则按模板原样展开）。

专题只决定技术领域的重心、必答项与可裁剪章节，**不承担过程义务**（迁移、兼容、回滚、等价性验证归场景）；多个专题叠加时同一章节取并集。详见 `references/focus-areas.md`。

### 按需加载

| 当下需要 | 读取 |
|----------|------|
| 场景判定、过程义务、按场景增删章节 | `references/scenarios.md` |
| 正文骨架与各节必答项 | `references/templates.md` |
| 专题加固点、必答项、可裁剪章节 | `references/focus-areas.md` |
| 容量/性能/可用性/成本的数字与口径 | `references/quantification.md` |
| 图规范、代码原则、反模式、评审清单、措辞 | `references/quality-bar.md` |

只读当前所需小节，不整篇搬运。

## 交付与收尾

1. 用 `write` 完整落盘并确认成功。默认命名 `{主题关键字}-design-{YYYYMMDD}.md`，存当前工作目录；用户指定了路径/命名则以用户为准。
2. 落盘前逐条过「交付前自检」，不通过就改。
3. 文档含 Mermaid 图时跑校验（脚本按自身位置相对定位，任一已注册路径都可用）：
   ```bash
   node <本skill目录>/scripts/check-mermaid.mjs <生成文件>
   # 常见注册位置：~/.config/opencode/skills/tech-design/、$DSH_HOME/skills/tech-design/
   ```
   `[MERMAID-ERROR]` 必须修复后重跑，**不静默放过**；`[MERMAID-WARN]` 为提示级。
4. 报告格式：`✅ 技术方案文档已生成: <文件路径>`，并补一句本次场景/档位/专题，以及文档中最需要评审拍板的 1-2 个点。
5. 按场景与档位生成评审检查清单（真源 `references/quality-bar.md`），作为文末小节或口头收口。
6. **不自动打开文件**（dsh Web 无 `code` 语义）。仅当用户明确要求且本机确有编辑器时才尝试，失败即提示手动打开路径。
7. 落盘后不做 `git add` / `git commit`。用户接着要独立 SVG 架构图或源码级验证时，分别提示 `svg-maker` / `project-insight`。

### 交付前自检（逐条过，任一不过就改）

- [ ] 每个性能/容量/可用性/成本数字都带**假设来源 + 口径（平均/P99）+ 时间窗口**？
- [ ] 非目标写成「超出范畴的用例」，并给了原因？
- [ ] 每个关键选型都有 ≥2 个备选，且写了代价与否决理由？
- [ ] 验收标准可验证（谁验、怎么验、阈值多少）？
- [ ] 场景对应的过程义务已落实：**改动类**写了影响面与兼容 + 回归范围？**结构重构**写了行为基线与等价性验证？**替换迁移**写了能力差异清单 + 对账 + 回退窗口？**下线**写了消费者盘点 + 下线判据？**专项优化**写了指标基线？**新建**删掉了现状与迁移类章节？
- [ ] 图中的每个节点/流程在正文都有解释，图与正文不矛盾？
- [ ] 不适用的章节已删除，而非留 "N/A" 或占位？
- [ ] 风险应对含触发条件与具体动作，不是"加强监控"这类空话？
- [ ] 所有未定项都收口到「开放问题」，并标了默认倾向？

## 注意事项

- 贴合业务规模：小需求不套企业级章节（成本/容灾/压测）。
- 考虑团队技术栈与运维能力的现实约束，方案要能落地。
- 选型客观中立，给 2-3 个方案与取舍理由。
- 保持可读：非技术人员能读懂核心思路，术语首现给中文释义。
