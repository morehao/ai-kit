# 模板档位（templates）

三档骨架决定**篇幅与评审范围**。三个维度各管一段，冲突时按右列：

| 维度 | 作用域 | 冲突时 |
|------|--------|--------|
| **档位（本文）** | 篇幅、评审范围、读者 | — |
| 场景（`scenarios.md`） | 叙事起点、过程义务、按场景增删章节 | 过程内容与章节增删听场景 |
| 专题（`focus-areas.md`） | 技术领域加固点 | 技术内容听专题 |

骨架综合了主流方案/设计文档实践：Google Design Doc 的「目标/非目标 + 备选方案」、Rust RFC 的「开放问题分类收口」、ADR 决策记录，以及国内评审的「验收标准 / 发布回滚」惯例（对照见文末）。

## 通用约定（读骨架前先读这段）

1. **骨架是覆盖清单，不是填空卷**。不适用的章节**删掉**，不要留 "N/A" 或一句话占位——占位章节比缺章节更伤可信度。
2. **骨架里的括号只允许是结构标记**（`（可选）`/`（如适用）`/`（按需）`），不写内容指令；内容的必答项在下方的「各节必答项」表里，**不要**把表里的说明抄进正文。
3. **章节增删优先听场景**：`scenarios.md` 的「章节增删」高于本文骨架。例：S1 新建要删「现状与问题」「兼容性与数据迁移」；S3 结构重构必须加「行为基线与等价性验证」。
4. **章节名是语义示例**，随主题替换；不加「1. 2.」数字前缀（用户明确要求编号时可在成稿时补，但不写进模板）。
5. **非目标用「超出范畴的用例」表述**，比否定句可评审：
   - 弱：「不做权限管理」。
   - 强：「超出范畴的用例：本期不覆盖跨租户数据共享、不提供字段级权限；原因是这两项需要独立的权限模型，计划在二期立项（见开放问题）」。
6. **验收标准必须可验证**：谁验、怎么验、阈值多少。凡涉及性能/容量/可用性的阈值，按 `quantification.md` 给推导与口径。
7. **不确定项集中收口**：评审需拍板的、实现中才能定的、范围外后续做的——分三类落在「开放问题」，不要散在正文里含糊。

## 档位速览

| 档位 | 目标篇幅 | 典型读者 | 定位 | 篇幅上浮/下沉信号 |
|------|----------|----------|------|-------------------|
| 轻量 | 1-2 屏 | 本模块开发者 / 一次评审 | 说清做什么、怎么实现、取舍与风险 | 出现跨团队评审、SLA 承诺、不可逆变更 → 上浮到标准档 |
| 标准 | 2-5 屏 | 团队评审 | 完整方案 + 详细设计 + 计划 + 验收 | 出现多系统联动、成本敏感、合规审查 → 上浮到完整档 |
| 完整 | 长文（分章节阅读） | 架构评审委员会 / 跨团队 | 全链路评估，含容量/安全/成本/回滚 | 只有单模块改动、无跨系统影响 → 下沉，避免过度设计 |

> 场景与档位的常配关系（如 S3 结构重构常配标准/完整档）见 `scenarios.md` 速览表，不要从篇幅反推场景。

## 轻量档

适用：单个功能模块、小型优化、简单集成。只回答「背景、思路、取舍、怎么落、有什么风险」，默认**不写**成本/容灾/压测/可观测等企业级章节。

```markdown
# [主题]技术方案

## 背景与目标
### 现状与问题
### 目标与非目标
### 验收标准

## 核心设计
### 设计思路
### 备选与取舍
### 技术选型
### 实现要点

## 实施计划
### 实施步骤
### 时间估算

## 风险与应对
### 主要风险
### 应对措施

## 待确认问题（可选）
```

**各节必答项**（✗ 标常见不合格写法）：

| 章节 | 必须回答 |
|------|----------|
| 现状与问题 | 当前怎么做、痛点具体在哪（S1 新建则整节删除）｜✗「现状有待优化」 |
| 目标与非目标 | 非目标 ≥1 条并给原因｜✗ 只写目标 |
| 验收标准 | 上线后如何衡量；**有指标影响时必须给指标与口径**｜✗「提升用户体验」；✗ 有指标影响却只写「评审通过即可」 |
| 设计思路 | 一句话能复述的核心做法｜✗ 只堆技术名词 |
| 备选与取舍 | ≥2 种做法 + 为何不选更重/更轻的那个｜✗ 单一方案 |
| 技术选型 | 1-2 句取舍理由 + 代价｜✗ 只写选了什么 |
| 实现要点 | 核心步骤或最小示例（代码原则见 `quality-bar.md`）｜✗ 贴整段实现 |
| 实施步骤 / 时间估算 | 步骤可独立验证；工期给区间 + 假设｜✗ 单点工期无假设 |
| 主要风险 / 应对措施 | 触发条件 + 动作（含回滚/降级）｜✗「加强监控」 |
| 待确认问题 | 需拍板的点 + 默认倾向｜✗ 待定项散落正文 |

## 标准档

适用：子系统、中型业务模块。在轻量档基础上补「现状痛点、约束与验收、总体方案、详细设计、里程碑、备选方案否决记录」。

```markdown
# [主题]技术方案

## 背景与目标
### 业务背景与现状
### 痛点分析
### 目标与非目标
### 约束与非功能需求
### 验收标准

## 方案设计
### 总体思路
### 总体架构
### 核心流程
### 备选方案与取舍
### 技术选型与理由

## 详细设计
### 模块划分与职责
### 接口设计
### 数据模型
### 关键逻辑与算法

## 实施计划
### 阶段与里程碑
### 资源需求
### 时间估算

## 风险评估与应对
### 技术风险
### 业务风险
### 应对措施

## 待确认与开放问题（可选）

## 附录
### 参考资料
### 术语说明
```

**各节必答项**：

| 章节 | 必须回答 |
|------|----------|
| 业务背景与现状 | 现状能力与数据流（S1 新建则删除）｜✗ 复述需求 |
| 痛点分析 | 痛点落到具体场景与频次，不是形容词｜✗「效率低」 |
| 目标与非目标 | 非目标写成「超出范畴的用例」并给原因 |
| 约束与非功能需求 | 性能/可用性/一致性/安全/合规的量化目标；可用性给端到端口径 + 串联预算（`quantification.md`） |
| 验收标准 | 量化指标 + 口径 + 验证方式 + 责任方 |
| 总体思路 | 一段话讲清方案主干与关键取舍 |
| 总体架构 | Mermaid 图 + 职责表（图规范见 `quality-bar.md`） |
| 核心流程 | 关键路径的时序或步骤，含异常分支 |
| 备选方案与取舍 | 自研/改造/引入现成/分阶段，各写代价与否决理由 |
| 技术选型与理由 | 组件级 2-3 方案：适用场景、代价、什么情况下不该选 |
| 模块划分与职责 | 职责不重叠 + **数据所有权归属** |
| 接口设计 | 接口清单 + 错误码 + 鉴权 + 幂等（`focus-areas.md` API 专题） |
| 数据模型 | 实体/字段/索引，且索引与查询匹配 |
| 关键逻辑与算法 | 按需保留；给边界条件与失败处理 |
| 阶段与里程碑 | 每阶段可独立上线 |
| 资源需求 / 时间估算 | 区间 + 假设（人力、依赖变化时如何调整） |
| 技术/业务风险 + 应对措施 | 触发条件 + 动作 + 验证，含降级与回滚 |
| 待确认与开放问题 | 分三类收口：拍板 / 实现中 / 范围外 |
| 附录 | 参考资料与术语；术语首现给中文释义 |

## 完整档

适用：系统架构、跨系统集成、技术重构、大型平台。在标准档基础上展开摘要、系统上下文、上线与回滚、成本、开放问题、决策记录等企业级章节。

```markdown
# [主题]技术方案

## 摘要（TL;DR）

## 背景与目标
### 业务背景与现状
### 痛点与动因
### 目标与非目标
### 约束与非功能需求
### 验收标准

## 总体架构设计
### 架构设计原则
### 系统上下文与依赖
### 总体架构
### 系统边界与职责
### 核心流程
### 数据流转

## 详细技术设计
### 模块划分与职责
### 接口设计
### 数据模型
### 存储设计
### 缓存设计
### 消息与异步（如适用）
### 关键算法与核心逻辑

## 方案与选型对比
### 备选方案
### 技术选型对比
### 选型风险与回退路径

## 性能与容量设计
### 性能目标与基线
### 容量规划
### 优化策略
### 压测方案

## 安全设计
### 认证与授权
### 数据安全
### 接口安全
### 容灾与备份

## 可观测性设计
### 监控告警
### 日志
### 链路追踪

## 上线与回滚方案
### 发布计划
### 兼容性与数据迁移
### 回滚方案

## 实施计划
### 阶段与里程碑
### 资源需求
### 时间估算
### 依赖与前置条件

## 成本分析
### 开发成本
### 运维成本
### 硬件/云资源成本

## 风险评估与应对
### 技术风险
### 业务风险
### 进度风险
### 应对措施

## 开放问题与后续工作

## 附录
### 参考资料
### 术语说明
### 决策记录（ADR）
```

**在标准档必答项之上，另加**：

| 章节 | 必须回答 |
|------|----------|
| 摘要 | 结论 + 核心取舍 + 量化目标 + 主要风险 + 需谁拍板（一页） |
| 痛点与动因 | 动因可追溯到业务或指标，不是「技术债」一句带过 |
| 约束与非功能需求 | 含**兼容约束**；可用性给端到端目标 + 串联预算表 |
| 架构设计原则 | 每条原则能对应到后文的具体取舍 |
| 系统上下文与依赖 | 外部系统/依赖方/数据来源与去向，可配 context 图 |
| 系统边界与职责 | 边界外的事明确不负责；数据所有权归属 |
| 数据流转 | 关键数据从产生到消费的完整路径 |
| 存储设计 | 访问模式、容量、一致性要求（`quantification.md`） |
| 缓存设计 | 失效策略 + 穿透/雪崩防护 + 一致性代价 |
| 消息与异步 | 按需保留；投递语义、幂等、积压与重试 |
| 选型风险与回退路径 | 选错的代价与回退成本 |
| 性能目标与基线 | 按 `quantification.md` 给推导与口径 |
| 容量规划 | 规划期总量 + 扩容触发阈值 |
| 优化策略 | 每项：预期收益 + 代价 + 回退开关 |
| 压测方案 | 场景、数据量、通过判据 |
| 安全设计 | 资产与信任边界、越权防护、日志脱敏（`focus-areas.md` 安全专题） |
| 可观测性设计 | 指标 + 阈值 + 告警触达；日志脱敏；链路追踪采样 |
| 发布计划 | 灰度/分批/开关，每步给进入与退出判据 |
| 兼容性与数据迁移 | **场景决定**：S1 删；S2 兼容期与数据兼容；S3/S4 迁移阶段 + 对账 + 回退窗口（`scenarios.md`） |
| 回滚方案 | 触发条件 + 步骤 + 回滚后验证 + 是否可逆；不可逆动作需审批 |
| 成本分析 | 单价 × 用量 + 计费口径，给区间 |
| 开放问题与后续工作 | 分三类收口：拍板 / 实现中 / 范围外独立做 |
| 决策记录（ADR） | 结论 + 备选 + 理由，便于日后回溯 |

> 完整档不内嵌「评审检查清单」章节：清单为单一真源，统一在 `quality-bar.md`，收尾时按场景与档位生成。

## 对齐的主流模板（维护备注）

- **Google Design Doc**：Goals / Non-Goals（非目标 = 本可以做但明确不做）、备选方案、系统上下文。
- **Rust RFC 模板**：Motivation 先行、Unresolved questions 分类收口。
- **ADR（Architecture Decision Records）**：决策以「结论 + 备选 + 理由」沉淀，落在完整档附录。
- **国内方案评审惯例**：验收标准、发布/灰度/回滚、排期与资源显式化。
